# 评审：证据优先设计的得与失（Canonical V2 设计返审）

Date: 2026-08-17. 作者：ZCode。触发：用户实测八组问题全面失败后判断"整个
设计过于强调证据，很多东西值得推翻重做"，要求找回设计文档逐条批判。
对象文档：`.agents/runs/canonical-v2-logical-rebuild/outcome-requirements.md`
（2026-07-11 效果需求基线）、`openspec/changes/rebuild-canonical-v2-knowledge-
platform/{proposal,design}.md`（Epic）、ADR-012~022、CONTEXT.md canonical 知识
术语、当日 serving-pack 覆盖审计。

## 一句话诊断

**设计不是被写错，而是被事故应激劫持。** 效果需求基线（7/11）写得平衡且
正确——"信息不完整不能整体消失""全面性与精准度同等重要""Coverage 与
Precision 分别达标"；但 7 月中旬的**破坏性测试事故**（design.md 开篇即此）把
整个架构的目标函数从"回答好问题"扭成"未经可验证证据不得动数据"。证据从
**保障手段**升格为**组织原则**，产品目标降级为"在可验证证据内回答"。

## 三层考古

| 层 | 文档 | 实际立场 |
|---|---|---|
| 效果需求 | outcome-requirements.md | ✅ 平衡：覆盖优先、硬排除最小化、覆盖是独立验收指标 |
| Epic 设计 | proposal/design + 22 个 ADR | ⚠️ 文字上保留平衡条款，结构上证据至上：7 个 capability 几乎全部以证据命名（recovery-evidence-landing / evidence-first-query-orchestration / grounded-progressive-answer…），每个环节配哈希、收据、资格判定、检疫 |
| 执行/数据 | 2026-08-01 一次性 restore | ❌ 源头就是旧 released 快照 + 手挑补充批次；四域现库从未流入；仪式成本使刷新从未发生 |

## 证据机器换来了什么（公平账，应保留）

1. **血统可验证**：candidate release、DB/索引同版、回滚——S12 系列多次实际
   依赖它脱险；8/13 的错实体能被定位修复也靠它。
2. **身份解析、断言保留、类型化关系**——数据质量脊柱，方向正确。
3. **多通道 + 透明披露**（查看检索过程）——形式保留，内容需重塑。

## 它杀死了什么（对照实测）

1. **证据成了准入门槛而非标注** → 服务索引只收"证据完备"对象：5,659 条
   （论文 0.6%、企业 27%）。效果需求原文"不能因为缺少 enrichment 就整体
   消失"被实现精确违反。
2. **仪式成本杀死了数据新鲜度** → 每批次要 decision bundle/embedding bundle/
   eligibility 物化，重建=92 任务级工程，从未对四域现库做过一次全量刷新，
   也没有任何"覆盖对账"环节（本审计本应是 build 产物）。
3. **证据不足 → 拒答** → claim-evidence 映射 + "重要事实必须有本地或当前 Web
   证据"在实现里变成：证据装配失败时输出"未找到 + 建议改问/外甩国知局"
   （P2/P4/P5）——精确违反效果需求 §5.1"回答先解决用户当前问题"。
4. **确定性压倒理解** → 设计明明写了"validated LLM-assisted retrieval plans"
   和"系统理解多轮指代"，实现却是 deterministic-planner-v1，LLM 只许改写
   视图不许做理解——P1/P3/P4/P6/P7 的直接根源。

## 推翻重做清单

| # | 推翻 | 重做为 |
|---|---|---|
| 1 | 证据=准入（eligibility 门控收录） | **证据=标注**：四域全量（~11.8 万对象）进服务索引；来源/置信/新鲜度为元数据，用于排序与披露；硬排除仅限需求原文四条（身份错误、终态合并、不安全、完全无事实） |
| 2 | 重建=92 任务仪式、一次性 | **数据供给常设化**（管线工序 0.5）：Postgres→pack 可例行、廉价、增量的刷新；保留哈希/同版校验但把成本降到"每周能跑"；每次 rebuild 产出覆盖对账报告（域计数 vs 源库） |
| 3 | 证据不足→拒答/外甩 | **回答优先**：本地缺就明说缺什么，然后继续用 web 正文/（标注的）模型综合回答；外甩外部数据库=产品事故 |
| 4 | 理解=确定性词表 | **理解层**（工序 1）：LLM 提案 + 确定性校验——设计本来就这么写，还债而已 |
| 5 | 查看检索过程=通道记账 | **理解与证据的展示**："系统理解为：关于X" + 用了什么证据 |

## 保留清单

Release/版本纪律（做便宜而非做罕见）、身份解析与断言保留（后台资产）、
多通道架构、产品四域边界、**效果需求基线本身**——重做应"回到 7/11 的
需求"，而非另起炉灶。

## 与八组实测的映射

P1/P3/P4/P6/P7（理解缺位）→ 推翻 #4；P2/P4/P5（拒答族）→ 推翻 #3；
P5/P8（数据覆盖）→ 推翻 #1#2；全部无法归因 → 观测线缺失（工序 9，另列）。

## 下一步建议

1. 用户过目本评审，裁定推翻清单；
2. 以"回到效果需求基线 + 管线九道工序 + 数据供给常设化"为新设计总纲，
   起草 supersede 性质的 OpenSpec change（Epic 级）；
3. 动工顺序：观测线 → 数据供给（全量入索引 + 覆盖对账）→ 理解层 →
   抓正文 → 融合保底/合成契约。
