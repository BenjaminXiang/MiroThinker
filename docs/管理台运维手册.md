## 0. 一分钟上手

1. 浏览器打开 <https://gxzx-coze-api.idea.edu.cn/main>。
2. 用户名固定为 `admin`（当前站点只有这一个管理员账号）。
3. 首次口令在服务器上，只有 root 能读：

   ```bash
   ssh root@100.64.0.96
   cat /root/deploy/fullstack-v2/var/admin-initial-password.txt
   ```

   文件权限 `0600`，内容为 16 位随机口令。**不要**把口令贴到聊天、邮件、工单或截图中。
4. 登录后，在首页「账号管理 → 修改我的口令」立即改密；确认新口令可以登录后，删除首启口令文件：

   ```bash
   rm /root/deploy/fullstack-v2/var/admin-initial-password.txt
   ```

5. 管理台各页面的入口在顶部导航；`/chat` 是对公众开放的问答页，不需要登录。

> 如果登录时报 `cross_site_request_refused`、`invalid_credentials`、`authentication_required` 或 429 锁定，直接看 [§11 常见问题](#11-常见问题按报错现象)。

## 1. 系统与访问概览

### 1.1 页面清单

| 路径 | 页面 | 是否需要登录 | 用途 |
|---|---|---|---|
| `/main` | 管理台首页（登录表单 / 仪表盘） | 是（登录页本身公开） | 登录、系统状态、快捷入口、账号管理 |
| `/admin` | 管理配置中心 | 是 | 采集、检索、存储、模型与连接、密钥 |
| `/browse` | 数据浏览 | 是 | 四域数据、证据、字段纠错、新增记录、企业文档上传 |
| `/logs` | 访问日志 | 是 | 会话/轮次、错误率、导出 |
| `/jobs` | 任务运维 | 是 | 定时任务、手动触发、运行历史 |
| `/upload` | 上传导入 | 是 | XLSX 上传、干跑、批次跟踪 |
| `/seeds` | Seed 管理 | 是 | 教授采集源、名册检查、抓取 |
| `/chat` | 对话 | **否** | 公众问答 |
| `/api/health` | 健康检查 | **否** | 返回 200 表示进程在 |

`/guoxian/...` 前缀是历史书签兼容入口（例如 `https://gxzx-coze-api.idea.edu.cn/guoxian/main`），nginx 会剥掉 `/guoxian` 前缀后转发到同一应用。**日常请统一使用 `/main` 这套根路径入口**，避免前缀路径下的大文件上传受额外限制。

### 1.2 浏览器与网络要求

- 推荐 Chrome / Edge 100+、Firefox 100+、Safari 15+；不支持 IE。
- 必须允许 Cookie（会话 Cookie 是 HttpOnly 的 `cv2_admin_session`）。
- 必须通过 HTTPS 访问；用 `http://` 直连服务器登录时，口令和会话 Cookie 都是明文传输，且 Cookie 不会带 `Secure`。
- 页面是服务端渲染的静态 HTML + 原生 `fetch`，不需要安装插件。

## 2. 登录、会话与账号管理

### 2.1 首次登录

1. 打开 <https://gxzx-coze-api.idea.edu.cn/main>。
2. 输入用户名 `admin` 和首启口令。
3. 登录成功后，同一个 `/main` 会切换成仪表盘（登录表单消失）。
4. 右上角显示当前用户名和「退出登录」。

首启口令的来源：

| 项 | 值 |
|---|---|
| 文件 | `/root/deploy/fullstack-v2/var/admin-initial-password.txt` |
| 权限 | `0600`，属主 `root` |
| 长度 | 16 位随机字符 |
| 何时生成 | 账号库为空时，服务首次启动自动播种 |
| 何时失效 | 在页面上改密、被其他管理员重置、或账号被删除后 |

> 账号库：`/root/deploy/fullstack-v2/var/admin-auth.sqlite3`（schema `canonical-v2-admin-auth-v1`）。口令只存 scrypt 加盐哈希，**明文永不落库**，所以口令找不回，只能重置。

### 2.2 口令与会话规则

| 规则 | 值 |
|---|---|
| 用户名长度 | 1–64 个字符，不能含空白 |
| 口令长度 | 8–256 个字符 |
| 系统生成口令 | 16 位随机字符，只在创建/重置成功时显示一次 |
| 会话 Cookie | `cv2_admin_session`，HttpOnly，SameSite=Lax；HTTPS 下带 Secure |
| 空闲超时 | 1 小时无操作后失效 |
| 绝对超时 | 登录后 12 小时强制失效 |
| 改密/重置/删号 | 立即让该账号的所有旧会话失效 |
| 登录锁定 | 同一「用户名 + 来源 IP」连续 5 次失败锁 1 分钟；继续失败翻倍，上限 30 分钟 |

**关于锁定的重要说明**：管理台在 nginx 后面，应用看到的来源 IP 是代理地址（当前审计里是 `192.168.40` 段），不是每个用户的真实公网 IP。因此，**锁定实际上是按账号生效的**：任何人连续输错 `admin` 口令 5 次，会让 `admin` 在所有客户端上一起被锁 1 分钟。不要反复试密码；被锁后按页面提示等待。

### 2.3 修改我的口令

1. 登录 `/main`。
2. 在「账号管理 → 修改我的口令」填写：
   - 当前口令
   - 新口令（≥ 8 位）
3. 点「修改」。
4. 成功后提示「口令已更新，其它会话已失效」；当前浏览器会话继续有效。

改密后：

- 其他浏览器/标签页的旧会话立即 401，需要重新登录。
- 首启口令文件如果还在，里面的旧口令已无效，建议删除。
- 不需要重启服务（登录每次读账号库）。

### 2.4 账号管理

「账号管理」区域只在登录后的仪表盘出现，所有账号都是 `admin` 角色（当前版本没有只读角色）。

| 操作 | 步骤 | 行为与注意 |
|---|---|---|
| 创建账号 | 「新账号」输入用户名 → 「创建」 | 服务端生成 16 位初始口令，**只在结果行显示一次**；刷新页面后看不到，必须当场记下并让本人改密 |
| 重置口令 | 账号列表 → 「重置口令」 | 立即生成新的 16 位口令并显示一次；旧口令和该账号所有旧会话立即失效；**点击即生效，没有二次确认** |
| 删除账号 | 账号列表 → 「删除」 | 立即删除；**点击即生效，没有二次确认**；最后一个账号不允许删除（返回 `last_account`） |
| 查看账号 | 账号列表 | 显示 `用户名（admin）`；不显示哈希、盐或任何口令材料 |

账号操作的审计记录在 `admin-auth.sqlite3` 的 `audit` 表，包含操作者、动作、目标、来源 IP、结果。可用只读方式查看：

```bash
sqlite3 -readonly -header -column \
  /root/deploy/fullstack-v2/var/admin-auth.sqlite3 \
  "select id, at, actor, action, target, source_ip, result from audit order by id desc limit 20;"
```

### 2.5 退出登录

- 右上角「退出登录」→ 调用 `/api/auth/logout`，清除 Cookie，回到 `/main` 登录页。
- 关闭浏览器标签页**不等于**退出；会话会一直保留到空闲 1 小时或绝对 12 小时。
- 在公共电脑上使用后，务必点「退出登录」。

### 2.6 忘记口令怎么办

按优先级选择：

**方案 A：还有另一个管理员能登录**

1. 用另一个管理员账号登录 `/main`。
2. 在账号列表找到 `admin`（或目标账号）→ 「重置口令」。
3. 把显示一次的新口令交给本人，要求立即改密。

**方案 B：唯一管理员也进不去，但有服务器 root 权限**

在服务器上直接改账号库。此操作不需要停服务，登录每次读库，WAL 下外部写入立即可见；新口令会打印在终端，旧会话立即失效。

```bash
cd /root/deploy/fullstack-v2
export PYTHONPATH="$PWD/code/apps/admin-console:$PWD/code/apps/miroflow-agent"
export CANONICAL_V2_ADMIN_AUTH_DB="$PWD/var/admin-auth.sqlite3"
.venv/bin/python - <<'PY'
from backend.services.admin_auth import store_from_environment, generate_password

store = store_from_environment()
password = generate_password()
store.set_password("admin", password)
print("new admin password:", password)
PY
```

执行后：

- 终端输出的就是新口令；**只留在本次终端**，登录后立即在页面改密。
- 旧口令、旧会话立即失效；不需要重启服务。
- 首启口令文件里的旧值已无效，建议删除该文件。
- 如果 `store_from_environment()` 报找不到库，确认 `CANONICAL_V2_ADMIN_AUTH_DB` 指向 `/root/deploy/fullstack-v2/var/admin-auth.sqlite3`。

**方案 C：连服务器也进不去**

需要平台交付方从宿主机/备份恢复。**不要**直接删除 `admin-auth.sqlite3`：那会丢失所有账号和审计记录（虽然下次启动会重新播种 `admin` + 新口令文件，但这是最后手段，且需要重启服务）。

### 2.7 登录失败排查顺序

1. 确认用户名是 `admin`，不是邮箱或姓名。
2. 确认读的是**当前**口令文件；如果改过密，文件里的值已失效。
3. 确认访问的是 `https://.../main`，不是 `http://...:18188/main`。
4. 看页面提示：
   - `invalid_credentials` → 用户名或口令错。
   - `locked` / 429 → 等提示秒数（5 次失败锁 1 分钟，翻倍到 30 分钟）。
   - `cross_site_request_refused` → 同源校验失败，见 §11.1。
   - `authentication_required` → 会话过期或 Cookie 没带上，重新登录。
5. 看服务器日志：`tail -n 100 /root/deploy/fullstack-v2/serve.log`。
6. 看审计表最近记录，确认失败/锁定/成功的时间线。

## 3. 首页仪表盘

登录后 `/main` 显示三块：

### 3.1 系统状态

页面把 `/api/canonical-v2/admin/system-status` 的**顶层字段**逐个显示成小卡片；对象类型显示为「N 个字段」，数组显示为「N 项」。当前版本常见的顶层字段：

| 字段 | 含义 | 怎么看 |
|---|---|---|
| `state` | 总体状态 | `ok` 表示接口正常；其它值先看对应子对象 |
| `generated_at` | 状态生成时间（UTC） | 判断数据是否新鲜 |
| `pack` | 发布包信息 | `release_id`、`build_run_id`、`record_counts`、`as_of`；`pack_dir` 可能滞后于实际启动参数（见 §4.4 警告） |
| `index_marker` | 检索索引绑定 | `state=ok` 且 `observed_sha256 == expected_sha256` 表示索引与发布版本匹配 |
| `freshness` | 四域新鲜度 | `pack_build_at`、`projection_as_of`、每域记录数；`collection_history` 在未配置 `DATABASE_URL` 时显示 unavailable |
| `operations` | 运行期存储 | 修正库、人工召回、访问日志的路径/条数/最早最晚时间、保留天数 |
| `storage` | 存储体检 | 各 SQLite 的 `quick_check`、表计数、文件大小；`milvus_db` 可能显示 missing（见 §11.10） |
| `disk` | 磁盘 | 各挂载点总量/剩余/使用率；当前 `/md1` 为 unavailable |
| `config` | 受管配置 | 配置文件路径、是否存在、schema 版本、字段数 |
| `collection` | 采集开关 | 四域开关、每轮 LLM/web 配额、执行窗口（UTC 小时） |

**判断顺序**：先看 `state` 和 `generated_at`，再看 `index_marker.state`、`freshness.state`、`disk`。某个子对象 `unavailable` 不一定影响问答，例如 `collection_history`、`milvus_db` 在当前线是已知形态；真正影响服务的是 `/api/health`、`/chat` 和检索是否正常。

## 4. 管理配置中心

入口：`/admin`。页面是**受管配置编辑器**，不是实时控制台：保存只写受管文件，运行中的进程不会热加载；大部分改动需要重启服务才生效。

### 4.1 通用规则（先读这一节）

| 规则 | 说明 |
|---|---|
| 保存只提交「脏字段」 | 只提交你改过的字段；没改的不会重写 |
| 空值 = 清除覆盖 | 把字段清空保存，表示回到默认/环境变量值，不是写入空字符串 |
| 环境变量优先 | 被环境变量覆盖的字段在页面上只读；页面不会制造「第二真相源」 |
| 保存 ≠ 测试 | 「保存本卡」只写受管文件；「测试连通性」是当场发起一次最小调用 |
| 保存 ≠ 生效 | 多数配置在服务启动时读取；保存后需要重启（见 §4.6） |
| 密钥只写不读 | 密钥明文不回显、不写日志、不写审计；页面只显示掩码和来源 |
| 受管文件 | `code/config/managed/settings.json`（普通配置）和 `code/config/managed/secrets.json`（密钥） |
| 权限 | 受管目录 `0700`；文件 `0600`；页面会警告权限异常 |

页面顶部的横幅在保存后会提示「已保存的改动需重启生效」，并给出重启命令。**注意：页面给的 `systemctl --user restart canonical-v2-backend` 是开发线命令，客户现场不适用**；现场实际命令见 §4.6。

### 4.2 采集与构建

卡片标题「采集与构建」，包含采集开关、配额、执行窗口和四域新鲜度。

| 字段 | 路径 | 默认 | 说明 |
|---|---|---|---|
| 企业采集开关 | `collection.enabled.company` | `true` | 关闭后采集调度跳过企业域 |
| 论文采集开关 | `collection.enabled.paper` | `true` | 同上 |
| 专利采集开关 | `collection.enabled.patent` | `true` | 同上 |
| 教授采集开关 | `collection.enabled.professor` | `true` | 同上 |
| 每轮 LLM 调用上限 | `collection.max_llm_calls_per_run` | `500` | 单轮采集允许的 LLM 调用数 |
| 每轮 web search 配额上限 | `collection.max_web_searches_per_run` | `200` | 单轮采集允许的 web 检索数 |
| 执行窗口起始（UTC 小时） | `collection.window_start_hour_utc` | `17` | 采集任务只在这个 UTC 小时之后启动 |
| 执行窗口结束（UTC 小时） | `collection.window_end_hour_utc` | `22` | 超过这个 UTC 小时不再启动 |

> 北京时间 = UTC+8。默认窗口 `17–22 UTC` 对应北京时间次日 `01:00–06:00`；调整前先确认现场时区和任务时长。

**各域新鲜度**表：

| 列 | 含义 |
|---|---|
| 域 | 企业 / 论文 / 专利 / 教授 |
| 记录数 | 当前发布包里的记录数 |
| pack 构建时间 | 发布包构建时间（UTC） |
| 距今 | 构建时间距现在多久；越大说明数据越旧 |
| 投影 as_of | 投影时点；正常情况下与 pack 构建时间一致 |

**采集状态行**：显示开关、配额、窗口、历史状态。`collection_history` 在未配置控制台数据库时不可用，这是当前现场的已知状态，不代表采集任务一定没跑。

**保存与生效**：

1. 修改字段 → 「保存本卡」。
2. 页面提示需要重启。
3. 按 §4.6 重启服务。
4. 重启后回本页确认字段值和运行期状态。

> 采集开关和配额在**服务启动/采集调度时读取**；被环境变量覆盖的字段（页面只读）改了也没用，要改服务环境。

### 4.3 检索与回答

卡片标题「检索与回答」，只放检索/回答自己的运行期开关；重排（rerank）的端点/模型/测试在「模型与连接 → 重排模型」，本卡不重复。

| 字段 | 路径 | 默认 | 说明 |
|---|---|---|---|
| 向量轨等待上限（秒） | `serving.vector_lane_timeout_seconds` | `8.0` | 向量道外层等待上限；超时只降级该道，不中断回答 |
| Web 轨主题相关性下限（kill switch） | `serving.web_topical_floor` | 未设置 | 控制 web 道是否启用相关性下限；改动前先做检索回归 |
| Rerank 单次最大文档数 | `serving.rerank_max_documents` | 未设置 | 仅在 rerank 启用时生效 |
| Rerank 超时（秒） | `serving.rerank_timeout_seconds` | 未设置 | 仅在 rerank 启用时生效 |
| 启动全量校验 | `serving.full_verify` | 未设置 | **只读展示**；由服务启动参数决定 |
| 挂载收据路径 | `serving.mount_receipt_path` | 未设置 | **只读展示**；由服务启动参数决定 |
| 轮次调试目录 | `serving.turn_debug_dir` | 未设置 | **只读展示**；用于转储每轮调试信息 |

**对话模型档位**（`serving.chat_llm_profile`）不在这张卡里，它在「模型与连接 → 对话模型」的下拉框中；一个字段只有一个入口。

**改动建议**：

- 不要为了「让回答更快」随意调大 `vector_lane_timeout_seconds`；它只影响等待上限，调大可能增加尾延迟。
- `web_topical_floor` 是 kill switch，改动会影响 web 道召回；改前必须跑检索回归/抽样题。
- rerank 默认未启用（当前站点 `rerank` 无端点）；启用前先确认端点、模型、超时和文档数，并做质量/时延对比。

### 4.4 存储与保留

卡片标题「存储与保留」，包含路径、库计数/体积、磁盘余量。

| 全部测试 | 卡片头部的按钮；按顺序逐个角色探针，不并发；结果显示在一个面板；某个角色没有端点时跳过并说明 |

#### 4.5.7 嵌入模型的特别警告

- 服务线向量模型身份由**发布包冻结**：页面只能改地址，模型名只读。
- 改嵌入地址会在重启后成为服务线真正使用的端点；**改模型名需要重建全部向量**，不能在页面上完成。
- 不要在没有重建计划的情况下切换嵌入端点/模型；否则查询向量与索引向量不一致，检索会退化或失败。换模型流程见仓库的 Embedding 一致性文档。

#### 4.5.8 Web 搜索

- Bocha 和 Serper 是两个独立 provider；端点由 provider 固定，页面不改写。
- 只改密钥；每个 provider 有独立的「测试连通性」和「保存本卡」。
- 两个都启用时，检索会按既有策略使用双 web 车道；禁用其中一个前先确认配额和召回影响。

### 4.6 配置生效与重启（客户现场）

**页面横幅里的命令不适用于客户现场。** 客户现场的服务是系统级 unit：

```bash
# 查看状态
sudo systemctl status miro-fullstack-v2 --no-pager

# 重启（会中断 18188，冷启动 + 预热需要数分钟）
sudo systemctl restart miro-fullstack-v2

# 跟踪日志
sudo journalctl -u miro-fullstack-v2 -n 200 --no-pager
tail -f /root/deploy/fullstack-v2/serve.log
```

说明：

- unit 文件：`/etc/systemd/system/miro-fullstack-v2.service`；`ExecStart=/bin/bash /root/deploy/fullstack-v2/run.sh 18188`。
- `TimeoutStartSec=2700`（45 分钟），`ExecStartPost` 有预热钩子；实际冷启动可能 6–10 分钟，期间 `/chat` 和 `/main` 不可用。
- **不要**在业务高峰重启；提前通知使用方。
- 页面横幅的 `systemctl --user restart canonical-v2-backend` 是开发线（`gpu01` 的用户级 unit），在现场执行会报 unit 不存在。

**保存后的验证清单**：

1. `curl -s -o /dev/null -w '%{http_code}' https://gxzx-coze-api.idea.edu.cn/api/health` → `200`。
2. `curl -s -o /dev/null -w '%{http_code}' https://gxzx-coze-api.idea.edu.cn/main` → `200`。
3. 登录 `/main`，确认 `系统状态` 的 `state=ok`。
4. 到 `/chat` 问一个已知问题，确认能正常流式回答。
5. 如果改的是模型/端点，跑一轮抽样题或 replay 门（见 §12.6）。
6. 看 `serve.log` 有无 401/403/5xx、模型连接错误、索引 marker 不匹配。

## 5. 数据浏览（含字段纠错、新增记录、企业文档上传）

入口：`/browse`。这是管理台里最常用的数据页：查看四域数据、证据和血缘，做字段级纠错、手工新增记录、上传企业文档。

### 5.1 页面结构

```text
版本概览（release / as_of / 四域摘要）
  └─ 数据目录
       ├─ 域页签：企业 / 论文 / 专利 / 教授 / Gaps·知识缺口
```

- 域名页签会写入地址栏 hash，例如 `#company`、`#paper`、`#patent`、`#professor`、`#gaps`；选中条目后 hash 里还会带 id，可以复制链接给同事（同事需要先登录）。

- 搜索框：`搜索当前域（名称、简介等任意字段）`；对当前域做子串匹配，点「搜索」执行，「清除」恢复全量。
- 列表默认每页 **25 条**；底部「上一页 / 下一页」和 `第 x / y 页 · 共 n 条`。
- 条目卡片显示名称/标题、关键字段、质量徽标（已核验/已验收等）；点击打开右侧详情。
- 如果当前域没有数据或检索不可用，左栏会显示空态/错误；错误信息会带接口返回的 message。

### 5.3 条目详情（右侧「证据与限制」）

选中条目后，右侧按以下区块展示：

| 区块 | 内容 |
|---|---|
| 关键字段 | 该域的主要事实字段；可编辑字段旁边有「改」按钮 |
| 证据标识 | 绑定当前发布版本的 evidence id/数量；只展示接口返回的标识，不在页面拼接 |
| 字段血缘 | `血缘记录 N 条`、`检索轨迹 N 条` |

### 5.4 字段纠错（覆盖层）

**可编辑字段**（只有这些顶层标量字段；其它字段会被服务端 422 拒绝）：

| 域 | 名称字段 | 可编辑事实字段 |
|---|---|---|
| 企业 `company` | `name` | `industry`、`geography`、`founded_at`、`profile_summary` |
| 论文 `paper` | `title` | `venue`、`year`、`citation_count`、`publication_date` |
| 专利 `patent` | `title` | `patent_type`、`publication_date`、`filing_date` |
| 教授 `professor` | `name` | `institution`、`department`、`h_index`、`citation_count` |

**操作步骤**：

1. 打开条目详情 → 在「关键字段」找到要改的字段 → 点「改」。
2. 在文本框中填新值。
3. 在「修改原因（必填，留痕）」中填写原因。
4. 点「保存」。
5. 保存成功后详情刷新，字段旁出现「已修正」徽标；鼠标悬停可看原值。
6. 下方「修正记录」出现本次修改；需要回退时点「撤销」。

**生效范围与限制**：

- 写入独立的 `corrections.sqlite3`（`/root/deploy/fullstack-v2/var/corrections.sqlite3`），**不改发布产物**。
- 浏览页立即生效；chat 回答随**下次构建**生效（构建时导出 active 修正记录作为输入）。
- 只允许顶层标量字段；`field_lineage`、`evidence`、`*_id` 等溯源/结构字段返回 422。
- 修改原因必填，操作人取当前登录用户名（`X-Remote-User` 已被彻底忽略）。
- 撤销是软撤销：历史保留，状态变为 reverted。
- 当前站点修正库为 0 条；如果保存后看不到「已修正」，先看接口错误提示（422/403/401）。

### 5.5 新增记录（手工录入）

入口：左栏「新增记录」按钮（Gaps 页签不提供）。

**表单**：

| 字段 | 必填 | 说明 |
|---|---|---|
| 名称 / 标题 | 是 | 企业/教授填名称，论文/专利填标题 |
| 补充字段（可选，JSON 对象） | 否 | 例如 `{"industry_tags": ["机器人"]}`；必须是 JSON 对象，不能是数组/标量 |
| 录入原因 | 是 | 留痕；会记录到覆盖层 |

**行为**：

- 提交后写入覆盖层，条目 `origin=manual`，显示「手工录入」。
- 手工新增记录**即时进入 chat 向量召回**（侧车 `manual-recall-v1`），不需要等下次构建。
- 页面**不提供删除按钮**；如果录错，可调用 `POST /api/canonical-v2/admin/records/{record_id}/revert`（空 body，需登录会话）或联系平台运维。撤销会 tombstone 对应召回点。
- 如果录入的是企业文档，建议用 §5.6 的「上传文档」，不要用「新增记录」硬塞长文本。

### 5.6 企业文档上传（即时召回）

入口：企业域页签（`#company`）→ 左栏「上传文档」。其它域不显示这个按钮。

**支持格式**：`.pdf`、`.docx`、`.txt`、`.md`、`.xlsx`；扩展名 + 文件头双重嗅探。

**Excel（.xlsx）**：先由 `backend/services/excel_structure.py` 识别表头与领域
（company/professor/patent/paper），预览返回 `analysis`（domain/confidence/mapping/row_count）。
`POST /company-documents/structured` 按识别结果写 raw 表：
`company`（信用代码/稳定 ID）、`professor`（+`professor_seed`）、`patent`（专利号）、
`paper`（DOI），统一 `quality_status='needs_review'`；同时写一份 manual-recall 文档。
纯文本“确认入库”路径仍保留。

**两步流程**：

1. **解析预览**
   - 选择文件 → 「解析文档」。
   - 服务端抽取文本，返回：抽取字数、召回块数、是否截断。
   - 限制：文件 ≤ **10 MiB**；抽取文本 ≤ **24,000 字符**（超出截断）；分块 ≤ **800 字符/块**、≤ **200 块/文档**。
   - 解析失败会显示具体原因（格式不匹配、无文本、PDF/DOCX 解析错误等）。
2. **确认入库**
   - 在预览文本框中检查/编辑全文（可直接改）。
   - 填写：
     - 企业名称（必填）
     - 文档标题（可选）
     - 关联已有企业 ID（可选；留空则作为新条目召回）
     - 入库原因（必填，留痕）
   - 点「确认入库」。
   - 成功后提示 `已入库 · N 个召回块即时生效`；文档列表出现该记录，状态「生效中」，带操作人和时间。
   - 需要撤销时点「撤销」；撤销后状态「已撤销」，对应召回点 tombstone。

**当前网关限制（重要）**：

- 应用层允许 10 MiB，但客户现场的 nginx **没有配置 `client_max_body_size`**，默认只有 1 MiB。
- 实测：直连 `127.0.0.1:18188` 上传 2 MiB 文件可以到达应用（返回 422 内容错误）；经公网 `https://...` 上传 2 MiB 文件被 nginx 直接拒绝，返回 **413 Request Entity Too Large**。
- 因此当前实际可上传的文件大约是 **≤ 1 MiB**；超过就会 413。
- 如需支持 10 MiB 文档，让平台运维在 nginx 的管理 API location 加：

  ```nginx
  client_max_body_size 20m;
  ```

  然后 `nginx -t && systemctl reload nginx`。这只放开请求体大小，不改变应用层的 10 MiB/24,000 字符/200 块限制。

**生效范围**：

- 企业文档上传**写入 chat 向量召回侧车**，不需要重建。
- **2026-10-22 实测限制**：Excel 上传、预览、确认入库均成功，`manual-recall.json` 点位数增加；
  但 chat 向量车道在测试问题中没有稳定带出上传内容（16 个 release 候选占满 top-16）。
  需要专用“上传资料”召回车道或后续修复；当前可保证“管理员文档列表可查”，不保证对话必答。
- 只影响企业域召回；不会修改发布包里的企业记录。
- 操作人取当前登录用户名，原因必填，列表可撤销。

### 5.7 数据编辑的生效时机（速查）

| 操作 | 浏览页 | chat 回答 | 备注 |
|---|---|---|---|
| 字段纠错 | 立即 | 下次构建 | 写 `corrections.sqlite3`；可撤销 |
| 手工新增记录 | 立即 | 立即 | 写 `manual-recall-v1`；页面无删除 |
| 企业文档上传 | 立即 | 立即 | 写 `manual-recall-v1`；可撤销 |
| 发布包/索引重建 | 重建后 | 重建后 | 属于发布操作，见 `/jobs` 和 §12 |

### 5.8 数据浏览的权限与留痕

- 所有写操作都要求登录会话 + 同源（`Origin` / `Sec-Fetch-Site`）；跨站写会 403 `cross_site_request_refused`。
- 操作人来自会话用户名，**不是** `X-Remote-User` 头；伪造该头无效。
- 字段纠错、手工记录、文档上传都会记录原因和操作人；审计/修正库可追溯。
- 不要把客户敏感文档上传到非企业域；当前只支持企业文档。

## 6. 访问日志

### 6.1 过滤与导出

| 控件 | 说明 |

> 导出文件包含用户提问和回答，可能含个人信息/业务信息；按现场数据管理制度保存和传输。

### 6.2 概览统计

页面顶部显示：

- 会话数、轮次、错误率、错误轮次、中断轮次、保留期。

### 6.3 会话列表与轮次详情

- 左栏会话列表按时间倒序，每页 20 条；显示会话首问、轮次数、时间等。
- 点击会话，右栏显示该会话的轮次：
  - 轮次序号、开始时间、耗时 `ms`、回答风格（`answer_style`）、提问类型、身份徽标、状态徽标。
  - 用户提问（question）。
  - 错误信息（status=error 时显示 `error_detail`）。
  - 系统回答（可折叠的「系统回答」）。
  - 引用来源（citations）列表。
  - 建议追问（suggested_followups）。

### 6.4 排查配方

1. **错误率升高**：状态选「错误」→ 按时间找第一个错误 → 打开会话 → 看 `error_detail` 和引用。
2. **某类问题答不好**：类型过滤 → 找代表性提问 → 对比正常回答的引用/时延。
3. **时延变慢**：看轮次的耗时列；再到 `/jobs` 看是否有构建/采集在跑，或看 `serve.log`。
4. **用户反馈**：到 `/browse#gaps` 看「回答不对 / 证据不足」的反馈台账，和日志里的同一提问对照。
5. **导出分析**：用 CSV/JSONL 导出当前过滤结果，注意脱敏。

### 6.5 保留期

- 默认 90 天（`paths.access_log_retention_days`，可在 `/admin` 的「存储与保留」改）。
- 页面显示的「保留期」是配置值；实际清理取决于服务器定时任务。**当前客户现场 crontab 只有 keepwarm，没有访问日志清理任务**（见 §12.7），所以日志可能超过 90 天仍保留。需要清理时按 §12.7 手工执行或加 cron。

### 6.6 身份与匿名

- `/chat` 是公开面，未登录用户的身份记为 `anonymous`；管理台自己的登录身份不会写进访问日志的提问身份。
- 不要用访问日志反推管理台账号；管理台操作在 `admin-auth.sqlite3` 的审计表里。

### 7.1 页面规则（先读）

- 同一个任务不会重复运行：正在跑的任务再点「立即运行」会被拒绝（`job_already_running`）。

### 7.4 手动运行一次任务

1. 在「任务清单」找到任务，展开分组（高级操作默认折叠）。
2. 如果任务有参数（域、模式、条数），先选参数；参数只接受白名单值。
3. 点「立即运行」。
4. 到「运行历史」看状态：
   - `运行中` → 等；
   - `成功` → 看条数/耗时；
   - `失败` → 点「查看」看 stderr 尾部；
   - `跳过` → 看原因（开关关闭 / 配额为 0 / 窗口外）。
5. 失败任务先排查，不要连续点击；连续失败 2 次会熔断。

### 7.5 运行历史与详情

- 过滤：任务、状态（成功/失败/跳过/运行中/熔断复位）。
- 列：开始时间、任务、触发（手动/周期/运维复位）、操作人、状态、耗时、条数、详情。
- 「查看」打开运行详情：
  - 基本信息、参数、触发方式、操作人；
  - stdout 尾部、stderr 尾部；
  - 「技术细节」折叠区（命令、cwd、超时、退出码等）。
- 「关闭」收起详情。

### 7.6 熔断复位

1. 先看失败详情，确认根因（配额、网络、数据库、脚本）。
2. 修复后点「复位熔断」。
3. 运行历史会出现一条 `breaker_reset`（触发=运维复位，操作人=当前登录用户）。
4. 再点「立即运行」重试。

> 不要用「复位熔断」代替排查；连续失败会再次熔断。

### 8.5 上传错误码

| 错误码 | 含义 | 处理 |
|---|---|---|
| `upload_unknown_domain` | 域不在白名单 | 用页面下拉项 |
| `upload_invalid_file` | 只接受 .xlsx 且不能为空 | 换文件/检查扩展名 |
| `upload_too_large` | 超过配置上限 | 压缩/拆分；同时看网关 413 |
| `duplicate_upload` | 同内容同域已上传 | 用返回的首次上传编号；不要重复传 |
| `upload_in_progress` | 同内容另一次上传正在准入 | 等几秒重试 |
| `upload_requires_postgres` | 没有构建期 PostgreSQL | 配置 `DATABASE_URL` 或联系平台 |
| `uploads_storage_unavailable` | 上传台账存储不可用 | 检查 `CANONICAL_V2_UPLOADS_DB` |
| `job_already_running` | 导入任务已有运行 | 等当前运行 |
| `job_invalid_params` | 参数被闸门拒绝 | 刷新/用页面选项 |
| `job_breaker_open` | 导入任务连续失败熔断 | 排查后 `/jobs` 复位 |

### 8.6 413 Request Entity Too Large

- 原因：nginx 默认 `client_max_body_size 1m`，而请求体（XLSX 或企业文档）超过 1 MiB。
- 判断：浏览器 Network 里看到 `413`，响应是 nginx 的 HTML 错误页，不是应用 JSON。
- 处理：平台运维在 nginx 的管理 API location 加 `client_max_body_size 20m;`（或按需更大），`nginx -t && systemctl reload nginx`。
- 应用层还有自己的上限（XLSX 128 MiB、文档 10 MiB），网关放开后仍受应用层限制。

### 8.7 上传的安全边界

- 上传需要登录会话 + 同源；跨站写 403。
- 文件只落构建期数据目录/批次台账；不会直接改发布包。
- 上传不绕过采集开关、配额、窗口、防重入、熔断。
- 上传的记录会写操作人（登录用户名）和时间；不要上传与业务无关的文件。

## 10. 安全、会话与审计

### 10.1 认证门禁覆盖范围

| 范围 | 未登录时的行为 |
|---|---|
| 管理页面 `/admin`、`/logs`、`/browse`、`/jobs`、`/upload`、`/seeds` | 302 跳转 `/main` |
| `/api/canonical-v2/*` 管理 API | 401 `{"detail":"authentication_required"}` |
| `/api/auth/*`（除 `/api/auth/login`） | 401 |
| `/main` | 登录表单（公开） |
| `/api/auth/login` | 公开（但受同源校验/限流） |
| `/chat`、`/api/chat*`、`/static/*`、`/api/health` | 公开 |

### 10.2 同源校验（CSRF 防护）

- 所有写方法（POST/PUT/PATCH/DELETE）在管理路径和 `/api/auth/*` 上都要通过同源校验。
- 校验逻辑：
  - 浏览器 `Origin` 必须等于服务端按 `X-Forwarded-Proto`/`X-Forwarded-Host`/`Host` 算出的 origin；
  - `Sec-Fetch-Site` 不能是 `cross-site` 或 `same-site`。
- 没有 CSRF token；同源校验就是这一层的全部 CSRF 故事。
- 失败返回 403 `{"detail":"cross_site_request_refused"}`。
- **不要**为了绕过这个错误去关闭同源校验；先检查反向代理的 `X-Forwarded-Proto`（见 §11.1）。

### 10.3 会话 Cookie

| 属性 | 值 |
|---|---|
| 名称 | `cv2_admin_session` |
| HttpOnly | 是（JS 读不到） |
| SameSite | Lax |
| Secure | 请求经 HTTPS 时带；纯 HTTP 不带 |
| Path | `/` |
| 空闲 | 1 小时滑动 |
| 绝对 | 12 小时 |
| 签名 | HMAC-SHA256，密钥 `var/admin-auth.key`（0600） |

- 修改/重置口令、删除账号会 bump `password_epoch`，该账号所有旧 Cookie 立即失效。
- 服务重启不会让会话失效（密钥文件持久化）；除非密钥文件被删除/替换。
- 多标签页共享同一会话；退出登录会让所有标签页失效。

### 10.4 登录限流

- 连续 5 次失败锁 1 分钟；继续失败翻倍（2、4、8…），上限 30 分钟。
- 键是「用户名 + 来源 IP」；由于反向代理，来源 IP 是代理网段，实际按账号共享（见 §2.2）。
- 锁定是**进程内内存**计数；重启服务会清空（但不要靠重启绕过锁定）。
- 429 响应带 `Retry-After`，页面显示剩余秒数。

### 10.5 审计

| 存储 | 内容 |
|---|---|
| `var/admin-auth.sqlite3` → `audit` | 登录成功/失败/锁定、登出、改密、重置、创建/删除账号；actor、target、source_ip、result、detail |
| `var/corrections.sqlite3` | 字段纠错、手工新增记录；operator、reason、old/new |
| `var/manual-recall-v1/manual-recall.json` | 企业文档上传/撤销；operator、reason、chunk_count |
| `var/access-logs.sqlite3` | 公开问答的会话/轮次、提问、回答、引用、时延、身份 |

- 管理台的身份取会话用户名；`X-Remote-User` 头被彻底忽略，伪造无效。
- 公开 `/chat` 记 `anonymous`，不记管理台账号。
- 审计表可用只读 SQL 查看（见 §2.4）。

### 10.6 密钥与受管配置

- 受管目录：`/root/deploy/fullstack-v2/code/config/managed/`（0700）。
- `settings.json`：非密钥配置；`secrets.json`：模型/搜索密钥；`secrets-audit.jsonl`：密钥变更审计。

## 11. 常见问题（按报错/现象）

### 11.1 `cross_site_request_refused`（403）

**现象**：登录、保存配置、改字段、上传等写操作返回：

```json
{"detail":"cross_site_request_refused"}
```

**根因**：管理台的同源校验比较浏览器 `Origin` 和服务端算出的 origin。公网是 HTTPS，但 TLS 在网关终止，网关用明文 HTTP 转到 nginx；如果 nginx 把 `X-Forwarded-Proto` 写成 `$scheme`（这一跳是 `http`），后端就会算成 `http://gxzx-coze-api.idea.edu.cn`，与浏览器的 `https://...` 不一致，所有写请求（包括登录 POST）都被 403。

**本现场已修复（2026-10-22）**：

- 新增 `/etc/nginx/conf.d/gxzx-forwarded-proto.conf`：

  ```nginx
  map $server_port $gxzx_default_proto {
      80      https;
      default $scheme;
  }

  map $http_x_forwarded_proto $gxzx_forwarded_proto {
      default $http_x_forwarded_proto;
      ""      $gxzx_default_proto;
  }
  ```

- `/etc/nginx/snippets/gxzx-proxy.conf`：

  ```nginx
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-Host $host;
  proxy_set_header X-Forwarded-Proto $gxzx_forwarded_proto;
  ```

- 备份：`/etc/nginx/snippets/gxzx-proxy.conf.bak-20261022-105749`
- 已执行 `nginx -t && systemctl reload nginx`。
- 验证：同源登录返回 401 `invalid_credentials`（说明已穿过同源门，进入认证逻辑）；伪造 `Origin: https://evil.example` 仍返回 403（CSRF 防护有效）。

**如果再次出现**：

1. `nginx -T | grep -n "X-Forwarded-Proto"`，确认加载的是 `$gxzx_forwarded_proto`，不是 `$scheme`。
2. 确认 `gxzx-forwarded-proto.conf` 还在 `conf.d` 且被 include。
3. 确认浏览器地址是 `https://...`，且页面不是从 `http://...` 打开的。
4. 检查网关是否改写了 `X-Forwarded-Proto`/`X-Forwarded-Host`；不要关闭同源校验来绕过。

**回滚**（仅当确认是新配置导致且需要恢复旧行为）：

```bash
ssh root@100.64.0.96 '
cp /etc/nginx/snippets/gxzx-proxy.conf.bak-20261022-105749 /etc/nginx/snippets/gxzx-proxy.conf
rm /etc/nginx/conf.d/gxzx-forwarded-proto.conf
nginx -t && systemctl reload nginx'
```

> 回滚后写操作会重新 403；除非网关侧已修正，否则不要回滚。

### 11.2 `invalid_credentials`（401）

- 用户名或口令错误。
- 确认用户名是 `admin`；确认读的是当前口令文件（改过密后首启文件失效）。
- 连续错 5 次会进入锁定；先看是否 429。

### 11.3 `authentication_required`（401）或页面跳回 `/main`

- 会话过期（空闲 1 小时 / 绝对 12 小时）、Cookie 被清、换了浏览器/设备。
- 重新登录 `/main`。
- 如果登录成功后立刻又 401：
  - 确认是 HTTPS，且浏览器允许 Cookie；
  - 确认系统时间正确；
  - 确认没有多个反向代理把 `Host`/`X-Forwarded-Host` 改得和浏览器地址不一致；
  - 看 `serve.log` 是否有 session 解析告警。

### 11.4 429 / `locked`

```json
{"detail":{"error":"locked","retry_after_seconds":60}}
```

- 同一账号连续 5 次失败；等 `retry_after_seconds`。
- 由于代理来源 IP 共享，别人输错也会锁到你的账号（见 §2.2）。
- 不要连续点击登录；不要靠重启服务绕过。

### 11.5 `current_password_incorrect`（403）

- 修改口令时「当前口令」填错。
- 用当前有效口令重试；如果忘了当前口令，走 §2.6 重置。

### 11.6 `account_exists` / `last_account` / `account_not_found`

| 错误 | 含义 | 处理 |
|---|---|---|
| `account_exists`（409） | 用户名已存在 | 换用户名或用现有账号 |
| `last_account`（409） | 不允许删除最后一个管理员 | 先创建另一个管理员，再删除 |
| `account_not_found`（404） | 账号不存在 | 刷新列表 |

### 11.7 口令长度/用户名校验（422）

- 口令必须 8–256 字符；用户名 1–64 字符且不能含空白。
- 页面通常会在提交前提示；如果接口返回 422，按 detail 修正。

### 11.8 上传按钮不见了 / `upload_requires_postgres`

- 当前 `postgres.available=false`（控制台没有 `DATABASE_URL`）。
- 页面会隐藏「上传」按钮，保留「干跑」和上传记录。
- 要启用正式上传：平台配置 `DATABASE_URL`（构建期 PostgreSQL）并重启；不要找页面开关。
- 如果只是验证表格解析，用干跑即可。

### 11.9 `console_database_not_configured` / Seed 管理不可用

- `/seeds` 页面提示「控制台没有配置数据库（DATABASE_URL）」。
- 首页「Seed 管理」快捷入口被隐藏；直接访问 `/seeds` 也会显示不可用。
- 这是当前部署状态；启用需要平台配置 `DATABASE_URL` 并重启。
- 不要重复刷新/点击；页面不会因为重试而恢复。

### 11.10 `milvus.db is missing` / `milvus_db unavailable`

- 当前 v4 索引目录以 `vector_matrix.npz` 为主，`milvus.db` 可能不存在；状态接口仍按旧结构检查，所以显示 missing。
- 判断检索是否正常：
  1. `/chat` 能否正常回答；
  2. `index_marker.state` 是否 `ok`，`observed_sha256` 是否等于 `expected_sha256`；
  3. `serve.log` 有无索引加载错误。
- 不要为了消除这个提示去创建空的 `milvus.db`；那可能让服务误判索引来源。

### 11.11 保存配置后没生效

- 页面保存只写受管文件；运行中的进程不热加载。
- 按 §4.6 重启 `miro-fullstack-v2`。
- 重启后确认页面字段值和运行期状态；如果仍不生效：
  - 字段是否被环境变量覆盖（页面只读）；
  - 是否保存到了另一份配置（检查 `code/config/managed/settings.json`）；
  - 是否改的是 `serving_pack_dir` 这类不控制运行参数的字段（见 §4.4）。

### 11.12 页面提示的 `systemctl --user restart canonical-v2-backend` 执行失败

- 那是开发线（gpu01 用户级 unit）的命令；客户现场没有这个 unit。
- 现场用：

  ```bash
  sudo systemctl restart miro-fullstack-v2
  ```

- 页面横幅的复制按钮仅作提示，不要在现场直接执行。

### 11.13 首页看不到「上传导入」「Seed 管理」

- 因为 `nav_auth.js` 探测到 `postgres.available=false`，隐藏了带 `data-requires-postgres` 的快捷入口。
- 直接访问 `/upload`、`/seeds` 仍可打开，但页面会显示不可用/降级说明。
- 这不是权限问题；登录账号仍是 admin。

### 11.14 删除/重置口令点击就生效

- 当前页面没有二次确认：账号列表的「删除」「重置口令」点击即执行。
- 重置会立即让该账号旧会话失效；删除不可恢复（账号/审计历史不保留）。
- 操作前确认目标账号；重要账号先创建替代管理员。

### 11.15 大文件上传 413

- 见 §8.6；当前网关默认 1 MiB，应用层允许更大。
- 需要平台加 `client_max_body_size` 并 reload nginx。

### 11.16 页面能打开但数据为空

- 数据浏览的空态可能是当前域没有匹配/发布包没有数据；先清除搜索、换域、看 `版本概览` 的记录数。
- 上传/Seed 的空态可能是数据库未配置（见 §11.8/§11.9）。
- 访问日志为空可能是时间过滤太窄；重置过滤。

### 12.7 备份（当前现场没有自动备份）

现状：`crontab -l` 只有 keepwarm（每 5 分钟），**没有** `backup-canonical-v2.sh` 或访问日志清理任务；`/md1` 也不可用。状态目录约 41 MB，建议每日备份到独立磁盘/远端。

**在线一致性备份（推荐）**：

```bash
TS=$(date +%Y%m%d-%H%M%S)
SRC=/root/deploy/fullstack-v2
DEST=/root/backups/mirothinker-$TS
mkdir -p "$DEST"

for db in access-logs corrections admin-auth jobs; do
  [ -f "$SRC/var/$db.sqlite3" ] || continue
  sqlite3 "$SRC/var/$db.sqlite3" ".backup '$DEST/$db.sqlite3'"
done

cp -a "$SRC/var/admin-auth.key" "$DEST/" 2>/dev/null || true
cp -a "$SRC/var/manual-recall-v1" "$DEST/" 2>/dev/null || true
cp -a "$SRC/code/config/managed" "$DEST/managed"

tar -C "$DEST" -czf "$DEST.tgz" .
rm -rf "$DEST"
echo "backup: $DEST.tgz"
```

注意：

- 不要用 `cp` 直接复制正在写入的 SQLite（WAL）；用 `sqlite3 .backup`。
- 发布包/索引约 4.3 GB，不要每天打进状态备份；在切包/重建前单独快照。
- 恢复：停服务 → 恢复 `var/` 和 `managed/` → 启动 → 验证登录/问答。`admin-auth.key` 丢失会让现有会话失效，但账号仍在，重新登录即可。

### 12.10 访问日志保留/清理

- 配置值：`paths.access_log_retention_days`（默认 90 天）。

- 需要清理时：先备份 `access-logs.sqlite3`，再由平台按表结构执行有界删除/重建；不要在服务运行时直接 `rm` 或 `cp` 数据库。
- 清理后 `VACUUM` 可回收空间（需要额外磁盘/时间；先确认没有长事务）。

### 12.11 常见故障的一分钟判断

| 现象 | 先查 | 命令/页面 |
|---|---|---|
| 页面打不开 | 服务/nginx | `systemctl status miro-fullstack-v2`；`curl /api/health` |
| 登录 403 | 同源/XFP | §11.1；用 `nginx -T` 查 `X-Forwarded-Proto` |
| 登录 401 | 口令/锁定 | §2.7；审计表 |
| 登录 429 | 锁定 | 等 `retry_after_seconds` |
| 管理页 302 | 会话 | 重新登录 `/main` |
| 回答很慢 | 模型/web/索引 | `/logs` 耗时；`serve.log`；`/jobs` |
| 回答报错 | 检索/模型 | `/logs` 错误轮次；`error_detail` |
| 上传 413 | nginx body limit | §8.6 |
| 上传/Seed 不可用 | `DATABASE_URL` | §11.8/§11.9 |
| 高级任务禁用 | `postgres_unavailable` | §7.3 |
| 磁盘满 | `/var/tmp` | `df -h`；清理 staging/旧备份 |
| 内存高 | 进程 | `free -g`；`ps`；重启需谨慎 |
