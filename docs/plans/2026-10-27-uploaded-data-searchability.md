# 上传的数据能被检索吗？两条通道，两种命运

> 结论先说：**企业资料文档（PDF/Word/简介）可以；XLSX 批量导入以前不可以，现在通过「增量桥」可以了。**

## 1. 两条上传通道

| 通道 | 入口 | 写到哪 | 能检索吗 |
|---|---|---|---|
| 企业资料文档 | 数据浏览页的文档上传 | manual-recall 存储（切块 + 向量） | ✅ 直接进检索 |
| XLSX 批量导入 | 上传导入页（企业/专利/教授） | 采集库（Postgres） | ❌ 以前不能；✅ 现在可以（见 §3） |

## 2. 证据（2026-10-27 实测）

- manual-recall 存储里有 **26 个 `upload_chunk`**：星尘产品材料、结构专利.xlsx、法本信息摘要、术语表等——这些文档一直在参与检索。
- 采集库里存在而 pack 里没有的记录：**3 家企业**（深圳留形科技、深圳鹏行智能研究、深圳鹏行智能科创）+ **47 篇论文**。
- 修复前问「深圳留形科技有限公司是做什么的」：8 条引用**全是网页**（manifoldtech.cn、猎聘、企查查……），本地数据一条没用到——因为服务只读 pack，导进来的行不在 pack 里。

## 3. 增量桥：采集库 → 服务

新脚本 `publish_collection_delta.py`：

1. 读采集库记录（企业按名称、论文按标题）；
2. 与 pack 比对，找出 **pack 里没有** 的记录；
3. 用与服务同一套 `ManualRecallStore` 写入 —— 记录 id 确定（`delta-<域>-<主键>`），重跑即替换；
4. 重启服务加载（manual-recall 是启动时加载的）。

**本次落地**：3 家企业 + 47 篇论文 → 存储点数 52 → 102，重启后生效。

**验证**：同一问题再问一次，引用里出现
`{"type":"company","id":"local-source-4c059f…","label":"深圳留形科技有限公司","url":null}`
——本地来源首次参与回答。

## 4. 边界与后续

- **容量**：manual-recall 是线性扫描。现在 102 点没问题；上千点需要评估延迟。
- **重启成本**：每次增量后要重启（约 10 分钟）。可以攒批：每天/每次导入后跑一次桥 + 重启一次。
- **长期解**：量级上来后，把增量合并进 pack（重建），桥只作为"重建之间的过渡"。
- **专利域**：采集库当前 0 条专利，桥暂无对象；导入后自动可用。
- **去重**：桥以 pack 的显示名为准。同名不同实体（极少）会被误判为已存在——后续可用统一社会信用代码/DOI 做精确匹配。

## 7. 专利导入：从 25 分钟卡死到 69 秒（2026-10-27）

客户 20 MB / 17,963 行专利表导入后一直「运行中」，CPU 99%，25 分钟一行没写。

**两个结构性原因（都是"每条记录重做一次"）：**

1. `link_company_ids` 每条专利都重建三张申请人→企业索引（约 7,000 次名称归一化）；
2. 写库循环**每条记录一个事务**（17,963 次提交）。

**修复：**

- `CompanyLinkIndex` 只建一次，穿进 `link_company_ids(index=…)`；
- 整批一个事务 + 每 500 条打进度。

**实测**：同一份文件 **69 秒**导入 17,963 条专利 + 10,808 条企业关联。

## 8. 导入即可查（端到端验证）

1. 采集库 17,963 条专利，其中 **6,191 条**不在 pack 里；
2. 用增量桥（bulk 写入，避免逐条重写整个存储）发布这 6,191 条 → 存储 6,293 点；
3. 重启（11 分钟）后验证：

| 问题 | 结果 |
|---|---|
| 有没有关于无菌围帘的专利 | 4 条引用，**3 条本地专利** |
| 基于 EtherCAT 总线的多轴驱控一体化伺服模块相关专利 | 7 条引用，**3 条本地专利**，回答直接复述专利权利要求要点 |

4. 评测门：**80/120**（基线 77）、product 26/27、verdict pass、无回归。
