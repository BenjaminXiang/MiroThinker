# 启动成本归因：690 秒里 71% 在"序列化 + 算哈希"（2026-09-20）

> 类型：分析（为什么问题会发生）· 写一次
> 触发：第 19 轮把 console 的遗留导入切掉后，重启**没有变快**（690s vs 680s），
> 于是把"启动到底花在哪"做成实测归因，而不是继续猜。
> 结论：**启动的大头不是加载数据、不是导入、不是读文件——是把已经封印好的不可变数据
> 反序列化成 pydantic 对象、再序列化成 JSON、再算一遍内容哈希。**

---

## 1. 方法（可复现）

- **不动活线**：不重启 18188。用 runner 自带的 scratch 包装（`serve_s12e_candidate.py`，端口 18199），
  **同一份命令文件**（argv 从活线进程 `/proc/<pid>/cmdline` 原样取出），实现同码同参同包。
- **隔离状态目录**：`CANONICAL_V2_ACCESS_LOG_DB` / `CORRECTIONS_DB` / `ADMIN_AUTH_DB` / `CHAT_GAPS_DB` /
  `TURN_DEBUG_DIR` 全部指向 `/tmp/boot-prof/state/`，实测 scratch 只写进了这个目录，操作者的账本零污染。
- **采样**：`py-spy record --rate 25 --duration 800 --format speedscope`。25 Hz × 706.9 s = 17,672 个样本，
  样本序号 / 25 就是秒数，所以"占比"与"墙钟秒数"是同一件事。
- 结果文件：`/tmp/boot-prof/boot2.speedscope.json`（临时物，不在仓库内）。

## 2. 结论

**71.4% 的样本落在"序列化 + 算哈希"这条链上**：

| 自耗时 top | 占比 | 是什么 |
|---|---|---|
| `model_dump` → `json.iterencode` | **62.6%** | 把 pydantic 模型整棵 dump 成 dict、再编码成 JSON |
| `_canonical_sha256` / `_sha256_text` | 8.8% | 上面那串 JSON 做 sha256（含 `serving_pack_loader:232`、`knowledge_read:153`、`complete_candidate_runner:93`、`index_projection:585`、`domain_projection_models:42`） |
| JSON 解析（`raw_decode`） | 4.8% | 反序列化输入 |
| 索引 / lookup | 1.8% | 打开 lookup.sqlite3 |
| 检索栈构造 | 2.2% | planner / knowledge_read 装配 |
| 导入（含 fastapi/uvicorn） | 约 1.7 s | 见 §4 |

按秒分组（每 100 秒一个窗口）：

| 窗口 | 序列化(喂哈希) | 序列化+算哈希 | JSON 解析 | 其他 |
|---|---|---|---|---|
| 0–100 s | 13.9% | 6.4% | **35.0%** | 42.4%（导入、包哈希、装配） |
| 100–200 s | **73.6%** | 6.5% | — | 19.8% |
| 200–300 s | **80.1%** | 11.4% | — | 8.4% |
| 300–400 s | **78.8%** | 7.9% | — | 13.2% |
| 400–500 s | 50.0% | 8.6% | 3.8% | 34.7%（含 Chromium 预热尝试） |
| 500–600 s | **68.4%** | 2.3% | 2.6% | 26.6% |
| 600–700 s | **82.6%** | 13.6% | — | 3.8% |

**从第 100 秒起，启动就基本只剩这一件事**。按 690 秒算 ≈ **490 秒**。

## 3. 是哪四个调用点在算

栈按"我们的帧"归并后，前 10 条链条全部落在四个入口：

| 入口 | 占比 | 位置 |
|---|---|---|
| `open_serving_pack_authority` → `pack_authority` | **约 20%** | `serving_pack_loader.py:999` 一带 |
| `create_serving_pack_knowledge_read` | **约 17%** | `serving_pack_loader.py:1965` |
| `create_serving_pack_query_planner` | **约 11%** | 同上族 |
| `_compose_pack_consumer_runtime` | **约 10%** | `complete_candidate_runner.py:798` |

四个入口做的事是同一件：**把从 `relationships.json`（3.3 GB）等文件读进来的对象重新构造成模型，
再 dump 回 JSON 去算一个内容哈希**——即"把一个刚读进来的不可变制品，用序列化的方式再证一次它没变"。

这也解释了日志里那 **23 MB 的 pydantic serializer warnings**：整棵对象图在 dump，每个字段都在报
"我序列化出来的东西可能不是你期待的类型"。警告是噪音，但它是**真干活的副产品**，不是无害的。

## 4. 被否掉的假设（同样要记）

- ❌ **"导入慢"**：实测 `import backend.main` 1.66 s（改前 2.61 s）——690 秒里占 0.14%。第 19 轮把
  2,298 个模块砍到 895 个，启动**没有变化**，现在有了原因。
- ❌ **"读文件/校验文件哈希慢"**：`hashlib` 自耗时 0%（文件按 8 MB 分块读，4.1 GB 只占几秒）。
- ❌ **"解析 JSON 慢"**：`raw_decode` 4.8%，集中在头 100 秒。
- ✅ **"反序列化 → 重新序列化 → 算哈希"**：71%。

## 5. 与既有裁定的关系

这条归因不是新问题，而是给一条**已确认的裁定**补上了数字：

- **R8 规则②「一处一次」**：制品已经在封印期证过一次（envelope/per-file sha256），
  读进来时再按模型 dump 一遍去算哈希，就是重复证明。
- **R8 规则③「热路径零证明」**：启动不算热路径，但它同样受"不可变数据直接信任"的约束。
- **R11 / P2「启动证明降级：parser/schema 版本绑定替代全模型重哈希」**：本次给出该条的**实测规模 ≈ 490 s**，
  也说明 P3（关系数据惰性/存储化，目标 boot ≤3–4 分钟）里的"惰性"比"存储化"更关键——
  真正贵的是**构造 + 再序列化**，不是读盘。
- **G10**（启动 12min11s、3.4GB 全图急加载）与 **G27**（切包窗口 ~13min，周更要求 ≤3–4min）：
  这条是它们的主因。

## 6. 下一步该动哪里（方向，不含实施）

1. **把"证明"钉到制品身份上，而不是对象图上**：pack 已有 per-file sha256 + manifest 身份；
   boot 只需**校验 manifest 与自身身份**（O(1) 元数据），不必对模型做 canonical dump。
2. **`_canonical_sha256` 的四个调用点逐个问 R9 六问**：它的读者是谁？热路径读者有吗？
   若读者只是"证明链自己"，按规则①「无读者即删」。
3. **`relationships.json` 的形态**（P3）：现在是 3.3 GB 单体 JSON，启动期一次性构造；
   若要保住启动预算，"惰性/存储化"要落到**构造**这一侧（按需查询），而不只是换存储格式。
4. 复核基线不回退（R9）：replay 7/7 + 两个逐字探针 + TTFT 对照。

> 提醒：任何一条落地前先确认它**不改变**答案内容与 trace 身份——这些哈希很可能同时被用作
> trace/引用的身份来源，删除必须连带处理身份语义，不能只删计算。
