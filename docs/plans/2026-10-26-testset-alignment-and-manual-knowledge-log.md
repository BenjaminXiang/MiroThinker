## 做了什么

### 1. 缓存写入 0 行：定位并修正校验门

- 线上日志显示所有候选都在 `local_only=False` 或 `citation_map=False` 被拒。
- 根因一：`local_only` 要求**全部**引用都是 `local-source-*`；实际答案几乎都
  是“本地 + 当前网页”混合，因此永远不满足。
- 根因二：`citation_map` 用 `TurnResult.citations` 校验，但 HTTP 信封只暴露
  `response.citations` 并重建 map；内部引用（如 manual）永远不在 map 里。
- 修复（客户机 bundle，已备份）：
  - 校验对象改为**将要重放的 HTTP 信封**；
  - `local_only` → `local_grounding`：至少一条本地引用即可，允许混合网页；
  - 纯网页答案仍不缓存；TTL 24h、release/data_epoch 失效逻辑不变；
  - 长度上限 1200 → 8000（真实答案 1–3k，原上限把大多数答案拒掉）；
  - 移除“名单墙”拒绝项（枚举答案的 8 家 + 计数尾巴是正常内容）。
- 离线校验：构造混合引用信封，`validate_candidate` 返回
  `True`（`local_grounding=True`、`citation_map=True`、`length=True`）。

### 2. 上传文档只被读到前 160 字

- `_semantic_text` 对所有本地字段统一截断 160 字；上传文档的正文在
  `profile_summary` 里，团队/全生命周期等后段事实根本没进 prompt。
- 修复：手动上传/人工记录（`source_authority=manual_upload`）的字段预算
  提高到 **800 字**（sidecar 单 chunk 上限），release 画像仍保持 160 字。
- 验证：法本信息答案从“缺全生命周期/客户服务团队”变为 5/5 命中；华力创科学
  5/5 命中（力传感器/Photon 系列/六维力传感器/光学传感）。

### 3. 控制符与 HTML 残留

- 线上出现 `<|end_of_answer|>` 与 `</br>`。前者已加入流式清洗与缓存拒绝
  片段；后者在最终信封清洗中删除。q26 复测已无 `<|end_of_answer|>`。

### 4. 用公开资料补全客户库（人工上传/人工记录，均可撤销）

所有内容均来自官网、央媒/权威媒体或论文页；找不到的条目不写入。

## 测评脚本适配性结论

原脚本**不适合作为严格测评**，原因不是模型，而是口径：

1. 19 条 head-turn 共用一个 `httpx.Client`，cookie 延续，第一条之后实际是多轮追问；基线数字被污染。
2. 用整个响应 JSON 做 required/forbidden 匹配，引用标签、query 回显都能“命中”，分数偏高。
3. 错误/超时行不进入 required 分母，失败会被静默吞掉。
4. `refusal_expected` 只记录 flag，不校验是否真的拒答。
5. 完全跳过 8 条多轮用例，`上述企业`/`他` 这类核心指代没有覆盖。
6. q23 的 required 含换行，逐字匹配天然失败。

已改为：

- `--mode head`：每条 head-turn 独立 cookie jar；
- `--mode full`：按 `turn_group` 顺序、每组一个 cookie jar，覆盖 27 轮；
- 只对 `answer_text` 打分，空白归一化后再匹配；
- 错误/超时计入 required 分母；
- 增加 `refusal_ok` 与 `refusal_misses`；
- 保存 answer_text、citations、latency、turn_index。

它现在是**可解释的回归门**，不是语义正确性证明：逐字 required 仍会低估同义表述（q22/q23），最终判断要结合逐题 answer_text。

## “浙江灵巧智能科技有限公司”为什么出现在灵巧手教授问题里（2026-10-26 04:00）

这家公司是真实存在的灵巧手公司（DexHand021 系列），和“灵巧手”主题相关，
但**和用户问的教授名单没有关系**，用户也没有提它。

根因不在 web provider，而在实体链接的短名派生：

- pack 里该公司 `aliases=["灵巧智能"]`；
- 实体名索引会对 alias 做“去行业词”派生，`灵巧智能` → `灵巧`（2 字）；
- 查询“有哪些做具身智能和灵巧手的教授”包含“灵巧手”，命中 2 字形式“灵巧”；
- 公司被绑成该轮主体，web lane 生成“浙江灵巧智能科技有限公司 + 原问题”的
  authority view；
- subject-consistency 门按这个公司主体过滤，75 条里丢掉 64 条，剩 11 条
  也不含教授名单，最终 0 引用。

因此：**不是整条搜索链路坏了**（provider 返回了 75 条，页面抓取也正常），
而是“实体链接短名 + 主体门”这一层有系统性风险：任何含 2 字品牌碎片的主题
问法都可能被劫持成公司主体。rewrite-view 过滤已加，但这次污染来自
authority/bound-entity 路径，不在 rewrite 过滤范围；web 门放行条件也没命中
（lane request 仍带 bound 实体）。

正确修法（尚未实施）：

1. **不再合成 2 字派生短名**：`_entity_name_forms` 只索引完整名、
   去法定后缀名和**显式 alias**；由 alias/全名再去掉行业词得到的 2 字形式
   一律不建索引。2 字品牌（华为/大疆）必须在 pack 里作为显式 alias 存在，
   不能靠算法派生。这样 `灵巧智能` 不会再派生 `灵巧`，而 `优必选`/`华为`
   这类显式 alias 不受影响。
2. 问法含“教授/学者/老师”时，不把 company 实体绑成该轮主体。
3. authority/rewrite view 统一做“不得引入原问题未命名的实体”校验。
4. 回归：q27 的 web views 不得出现任何公司全名；subject gate 至少保留
   若干“教授/高校/实验室”页面。

**不采用 blocklist**：把“灵巧/智能/感知/工业/医疗…”加入黑名单是打补丁，
既漏（任何未列出的 2 字词仍会中招），又误伤（真实 2 字品牌被屏蔽）。
根因是“算法合成 2 字短名 + 中文子串匹配”，应在索引生成侧消除合成短名，
而不是在匹配侧穷举坏词。

当前 q27 仍 0/4，不能算修复。
