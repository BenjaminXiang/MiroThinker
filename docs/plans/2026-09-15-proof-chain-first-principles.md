# 服务期"证明链"的第一性原理复盘与收敛路线（2026-09-15）

> 定位：用户裁定"第一代的 isolated index target 证明链已是过度设计、与需求不符"后的系统级梳理：
> 需求 → 威胁模型 → 现状成本 → 目标形态 → 分阶段收敛。
> 状态：一次成文（write once）。关联：`serving-index-process-scope`（P0，在飞）、
> `reduce-rebuild-validation-cost`（封印侧）、`2026-09-15-milvus-role-in-serving-analysis.md`。

## 1. 需求（只列服务真正要的）

| # | 需求 | 含义 |
|---|---|---|
| R1 | 查得准 | 数据在**入库/构建**时干净准确（离线质量门、离线清洗）——服务期不承担"再证明数据对" |
| R2 | 查得快 | TTFT ≤30s（本地优先、置信足够可提前收口）；**启动与更新不许吃掉可用性** |
| R3 | 查得全 | 四域覆盖 + web 补全 |
| R4 | 回复得好 | **引用可回溯**（每条答案追到源）——这是产品级证据需求 |
| R5 | 可运维 | 周/月全量重建（boring 流程）、可回滚、客户现场（单机、无 GPU、无额外基础设施）可部署 |

**关键区分**：R4 的"证据"是**面向用户的答案级可追溯**，不是"每个字节在每次启动时重证"。

## 2. 第一性原理：服务启动时究竟需要证明什么

| 威胁 | 后果 | 现行代价 | 更便宜的等价证明 |
|---|---|---|---|
| 挂错包（错 release/错嵌入模型/错域集） | 答案与引用全错 | 全链回读 | release_id + marker sha + embedding_model_id 三处对齐（毫秒级） |
| 文件截断/写坏 | 崩溃或静默错数据 | 全量行级回读 | 文件大小 + 首尾块/抽样指纹；全量 sha 仅在发布验收跑 |
| 位腐烂 | 同上 | 全量 sha | 存储层校验 + 可选全量模式；风险与成本显式取舍 |
| 拿到过期包 | 用户看到旧数据 | 无（靠流程） | 启动绑定 + 健康检查暴露 release_id + 单一命令文件切包 |
| 代码升级导致解析语义漂移 | 静默语义错 | **全模型启动期重哈希** | manifest 增 parser/schema **版本绑定** |
| 构建期误写生产目录 | 数据被覆盖 | forbidden-path 隔离 | **保留**（一次性、构建期、成本≈0） |

⇒ 服务启动的正确命题是：**"这是哪个被批准的包、它是否完整、它是否新鲜"**——
不是"每个字节都再证一遍"。

## 3. 现行链条的成本账（实测）

| 项 | 实测 | 性质 |
|---|---|---|
| 启动包装载 | **≈12min11s**（journal：unit start 00:40:17 → uvicorn ready 00:52:28） | 其中 relationships.json `sha256`=4.1s、原生 `json.load`=65.8s → **余额≈10 分钟是模型重建/校验**（未打点；boot receipt 将补上） |
| 索引打开 | ≈60s（10.2s 产物哈希 1.67GB + **~50s Milvus iterator 超时空转**） | 空转 |
| pack 体积 | 4.8GB，其中 **1.03GB `milvus.db` 无查询消费者** | 死重 |
| 启动失败 | **5 天 2 次**（09-11 index-v1、09-15 index-v2）：`Open … milvus.db failed, the file has been opened by another program` → 整个 boot 失败、systemd 重启才活 | **可用性依赖一个从不查询的文件的单写锁** |
| 每次会话 | 重装载 + 重复哈希（agent-35 在修） | 已立项 |
| 封印侧 | envelope_validate 2071s / index_snapshot_verify 54.4s / dogfood_open 351.1s | **一次证明，位置正确——保留** |

**修正一个先前的粗略说法**：12 分钟启动的主因**不是**"证明链"，而是**全图急加载**
（3.4GB relationships 一次性解析进内存 + 模型重建）。证明链贡献的是 60s + 1.03GB +
单写锁故障类 + 每会话重证。两者要分开治。

## 4. 裁定：哪些是过度设计，哪些真有用

- **保留（轻量形态）**：构建期隔离守卫（forbidden paths）；marker / release / 嵌入模型身份；
  per-file sha（封印期算一次即可）；receipt 计数（运营有用）。
- **降级/搬走**：全量行级回读（Milvus）；启动期全模型重哈希/规范化；每会话重装载。
- **退役**：Milvus 在服务包中的角色（依据：无 ANN、无查询消费者、单写锁故障×2、
  [角色分析 §7](./2026-09-15-milvus-role-in-serving-analysis.md)）。

## 5. 目标形态：一个权威副本 + 一次证明 + 三种便宜校验

- **一个权威副本**：release 目录 = lookup.sqlite3 + vector_matrix.npz + relationships.json
  （+ catalog/manifest）。Milvus 自新 release 起退出服务包（构建/审计若仍需，另存于构建侧）。
- **一次证明**：全量证明留在 **seal 期**（已有三件套），产出 receipt：每域计数 + 文件哈希 +
  解析器/schema 版本 + 耗时。
- **启动三验**：身份（release/marker/model 对齐）＋ 完整（大小 + 首尾/抽样指纹；
  全量 sha 作可选模式供 CI/发布验收）＋ 新鲜（receipt 与 bundle 对齐；健康检查暴露 release_id）。

> **白话版（为什么是这三样）**：
> ① **一个权威副本**——一份数据只留一个"真身"；有第二份"真身"就必须不断证明两者一致
> （现状：Milvus 副本 vs npz 矩阵，逼出逐行回读、1.03GB 死重与单写锁故障）。
> ② **一次证明**——对"这份数据是对的"做一次全量证明，放在**没人等的地方**（封印期），
> 并签一张收据（哈希/大小/计数/版本/耗时）；证明不删除、只搬层。
> ③ **边界验据**——数据进入服务进程的那一刻只做三件便宜事：查身份（是否我批准的包）、
> 查完整（有没有被截断/破坏）、查新鲜（是不是当前该跑的版本）；进内存后就当它是真的，
> 进程余生不再复查（数据只读、不会变）。
> 一句话：**多副本制造证明义务；证明做一次就够；边界过后不必再看。**

## 6. 收敛路线（各自可独立落地与回滚）

| 阶段 | 动作 | 预期收益 | 依赖/风险 |
|---|---|---|---|
| **P0（在飞）** `serving-index-process-scope` | 进程级装载 + 启动预热 + 轻量挂载校验 + boot receipt；Milvus 移出打开路径 | 去 ~50s；每会话不再重装重证 | 无 |
| **P1** pack 契约 | `milvus.db` 退出服务包；npz 校验锚改 lookup 回读 | −1.03GB；**启动失败类根除**（单写锁消失）；少读 1GB | 属 pack 契约变更，独立 change；run16+ 起生效，历史包不动 |
| **P2** 启动证明降级 | 大文件不在启动期重哈希（沿用 seal 证明）；manifest 增 parser/schema 版本绑定（替代全模型重哈希）；boot receipt 落计时 | 让 12min 中"可回收部分"显形并回收 | 需明确"轻校验"边界；保留全量模式开关 |
| **P3** 数据形态（最大杠杆） | 12min 主因＝3.4GB 全图急加载：改为**惰性/按需装载**或 **relationships 存储化（SQLite + 索引）**；与 C6 周期更新一起设计 | boot 目标 ≤3–4min；周更窗口缩短 | 结构性改动，独立立项（重建成本分析 §13 已指向"信封契约重构"） |

## 7. 边界与风险

- **不删**构建/发布侧的全量审计（那是"一次证明"的正确位置）；
- 位腐烂只靠"大小+抽样"覆盖不全 → 保留全量 sha 作为**发布验收/CI 模式**，取舍写进 spec；
- 每步保留旧路径开关（env），切包仍走单一命令文件 + `systemctl --user restart`；
- 历史产物（index-v1/index-v2 的 milvus.db 等）**保留不删**，仅新 release 采用新契约。

## 8. 验收（各阶段）

- **P0**：进程级打开计数=1/进程；boot receipt 有数字；门禁 7/7 + 探针逐字不变；
- **P1**：新 pack 无 milvus.db、boot 不再打开 Milvus；启动失败类归零（观察期 ≥1 周含 1 次切包）；replay 门 7/7；
- **P2**：boot receipt 的 phase 分解（对照 12min11s 基线）；冷启 TTFT；回滚演练通过；
- **P3**：立项时定目标（boot ≤3–4min、C6 周更窗口 ≤10min），以 receipt 为度量。

### 9.3 审计结论

系统当前在证明的是三类东西：

1. **需求真正要求的**（O1–O7）：只占少数，且多数本就便宜（身份对齐、引用绑定、消毒）；
2. **实现细节的自我一致性**（大头）：content-addressed ids、全图重哈希、逐行回读——
   证明的是"我的实现是自洽的"，**没有任何读者会去用它**；
3. **证明完没人消费的**：placeholder 普查（warn-only）、Milvus 回读、
   boot 重做 seal 已做过的活。

**"一切可证明"的真正代价不是严谨，而是把实现细节当需求来证明，并且因为不信任
任何一份收据而三处重证。**

### 9.4 三条证明规则（供 P1–P3 及今后设计使用）

1. **每条证明必须有一个"读者"**（用户 / 运维 / 发布门）——找不到读者的证明＝删除；
2. **同一事实只在一处证明一次**（最早能证明的层）；下游只验"收据身份"，不重放证明；
3. **热路径零证明**：已验证且不可变的数据（索引/快照/矩阵）在进程内**直接信任、不再对号**；
   热路径只保留两类动作——① 干活本身（检索/排序/合成/引用渲染/缓存派发）；
   ② 把关**当回合新进入系统的外部数据**（用户输入 / web 抓取 / LLM 输出）——它们不在任何
   开机证明的覆盖范围内。

**展开（2026-09-15 补充）**：

- **规则 1 的"读者"**＝会消费证明结果的角色：用户（引用可核对）、运维（收据/健康检查）、
  发布门（阈值不过则拒发）、下游程序（用 id 去重/绑定）。判据三问：**谁消费？没有它会怎样受损？
  该受损能否被别处覆盖？**——三问皆答不出即删。
  反例：`placeholder_scan`（warn-only，构建从不因它拒发）＝一个没有读者的数字；Milvus 行级回读＝
  一份没有读者的全量证明。正例：per-file sha256（读者＝运维，"挂错包/截断"受损）。
- **规则 2 的"最早层"**：证明成本随"离在线越近"越贵（离线 34min 可接受；启动 34min＝停机；
  放到查询里＝TTFT）。实现形态＝**收据**：最早层做全量证明并落收据（哈希/大小/计数/版本/耗时），
  下游只验"收据 + 文件身份"，不重放证明。现状病根：seal 的 `dogfood_open`（351s）已证明
  "包能开且权威一致"，boot 又重做 12min——**因为没有任何一份收据被信任**。
- **规则 3 的"热路径零证明"**（09-15 追问后收敛）：信任只在**边界**上建立一次（加载/开机 +
  收据），之后到进程退出，只读内存里的数据**不再复查**——对不会变的东西对号，本身就是重复证明
  （违反规则 2）。热路径允许的两类动作：① 干活本身（检索/排序/合成/引用渲染；缓存命中判断属
  "派发"而非"证明"）；② **当回合外部数据的把关**（用户输入、web 内容、LLM 输出——它们不在
  开机证明的覆盖内）。实测反例：`bind_trace`（每对象 2 dump + 3 哈希＝**重新造号**，占查询
  窗口 26–36%）、`_matches_vector_request`（每查询 5.1 万次 `json.loads`）、每车道重复的请求
  自洽校验。允许的例外：O(答案条数/引用数) 的绑定（claim→evidence）——随输出增长，不随语料增长。
