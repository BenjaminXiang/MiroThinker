## 发现了什么

1. **"空行"其实是"未绑定但有名字"**：4,951 行申请人不是空行——`company_name` 为空，但 `name`
   都是真公司名（`深圳先进技术研究院`、`优理奇机器人科技（苏州）有限公司`…）。**移除=删掉 4,951 个
   真名**，而 D1 的企业绑定正需要它们；且"未绑定"这个状态本来就是 `canonical_company_id: null`
   ——`_direct_patent_applicant_scan` 过滤用的正是这个字段，所以保留不动、语义不变。另外实测
   **0 条越界绑定**（所有绑定都指向已发布公司）。
2. **重复边的成因是两条 link 家族**：同一条 (教授, 论文) 关系既来自保留的历史
   `PROF-PAPER-LINK-*`，又来自 P4 salvage 的 `p4-professor-paper-link:*`。去重的锚点因此放在
   **链路装配处**（不是边投影处），并且在装配前去重前已把源记录血统并入端点身份，所以删掉重复链路
   不丢血统。
3. **死字段"删除"不是清洗规则**：目录（catalog）被内容哈希钉死在两处，投影模型 `extra="forbid"`，
   而读侧 `knowledge_read_isolated._read_public_projection` 要求"发布文档 == `model_dump_json()`"。
   在这三条约束下，删字段必须三处同步改（目录 + 模型 + 所有读者）＝一次**发布身份变更**。本批因此
   只做"决定表 + 每次构建可见的度量"，把退役留给一次专门的目录修订（见风险）。
4. **度量口径差 3**：我测得 49 个死声明（论文 17），首遍报告 46（论文 14）——差的正是
   `paper.enrichment_sources / funders / summaries` 三个字段，首遍未列；公司/教授/专利三个域的数量
   与首遍完全一致。
5. **venue 合并键比首遍更强**：首遍的口径 121 组 / 244 标签 / 1,979 行；本次因为额外剥离
   `the/of/on/in/for/and` 与 `Proceedings of`、并在"规范形"上再分组（年份/括号剥离后会与新组相遇），
   合并到 153 组 / 326 标签 / 2,684 行；唯一标签 5,031 仍满足首遍自己的验收线 ≤5,083。
