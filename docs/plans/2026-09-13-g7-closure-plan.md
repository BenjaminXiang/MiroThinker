# G7 修复规划：具身智能清单稳定召回龙头（2026-09-13）

> 定位：replay 门唯一残留失败（G7 重复 2/3 缺"优必选"）。
> 关联：change-id `retrieval-v2-derived-index-and-fusion`（1b.1/1b.3）、
> `close-workbook-gaps`（C1）；执行日志条目 38。

## 现象与定量（26 轮历史 + 今日 3 跑）

- 查询「深圳有哪些做具身智能的公司」重复 3 次：**本地召回窗口 0/3 含优必选**
  （历史总计 6/26，约 23%；在窗口内时排 ~37/128）；
- **commit 宇宙 0/26** 含优必选——即使进了窗口也从未真正进入会话已答集；
- 少数通过的次数（今天 r1/r3）是 **web 散文顺带提及**（引用里 0 条优必选）——
  web 运气，不是本地能力。这正是"查的准/全"要消掉的不稳定源。

## 根因（全部定位到代码）

1. **并列组按哈希切窗口**。F1 类目召回的打分排序是
   `(-score, domain, canonical_object_id, document_id)`：查询「具身智能」拆成
   bigram{具身,身智,智能}，「智能」恰好在 industry=人工智能（约上千家）命中
   ×8 分；优必选同样只在 industry 档命中 8 分——与上千家**并列**，窗口（枚举
   最多 64）按对象哈希 id 截断，它排多少名全看哈希。
2. **差异信号被"每词只计最高档"吞掉**。优必选 tech_tag「人形智能机器人
   研发商」本可命中 智能机器人/机器人/人形 等更强证据，但当前查询词里没有
   这些词，而"智能"已在 industry 档计过 —— tag 证据不再产生任何加分。
3. **commit 通道依赖答案文本命中**。枚举回合的 commit 是"已选 ∪ 答案中提到
   （按 display_name 形态匹配）∪ 覆盖句列名"；历史 6 次在窗却 0 commit，
   说明"覆盖句已提及不重复列"与"名字形态匹配"之间有一个让本地 handle 失去
   join 机会的缝——需要用当前代码做一次受控复现钉死（修复前先证伪）。

## 修法（确定性，分两片）

**G7-a 召回侧（无重建，serving + 声明数据）**

- A1 声明新增「具身智能」同义族（`expands` 机制已有 PCB 先例 16 条）：
  成员候选 人形机器人/智能机器人/人形（带降权乘数）；成员进入查询词后
  直接命中优必选 tech_tag → 高分脱离平局组；
- A2 平局改进（通用）：排序键在分数后加入"证据丰富度"（命中档数/词数），
  有技术标签差异的公司排在纯 industry 平局之前；
- A2b（新增，2026-09-13 复核"身智"现象后登记）：**词表感知的整词抽取**——
  4 字以上的残段目前只按重叠二元组拆（「具身智能」→ 具身/身智/智能），
  短语级信号被稀释为三个 1 权词、由最泛的「智能」(4,233 篇) 主导；改为：
  先匹配锚定声明的已知词条（具身智能就在声明里），命中则保留整词（2 权），
  二元组仅作兜底。实测「身智」81 篇中 80 篇含完整短语——跨界二元组本身
  无害，但短语特异性丢失是平局问题的另一半；
- A3（视 A1/A2 效果再定）：结构字段（tech_tags 锚定词）命中公司在桶截断前
  保底配额；不追求"全部公司"（web/补数据兜底其余）。
- 验收：离线 4 个 view 变体 rank ≤32 ≥90%；live 重复 3/3 窗口含优必选；
  兄弟龙头（越疆/乐聚/众擎/逐际，如果在库）同口径。

**G7-b commit 侧（代码）**

- B1 受控复现：构造能召回优必选的查询，追踪"覆盖句生成 → commit join"；
- B2 修：窗口内本地公司 handle **只要能以可提及形态（含短称）在答案文本
  命中就必须 join**；覆盖句"不重复列名"的文案行为保留，但不允许它成为
  唯一 join 通道；
- 验收：召回在窗时 commit 宇宙 3/3 含优必选；答案文本 3/3 含优必选；
  另跑一次"web 关闭/本地证据"受控证明，证明不靠 web 运气。

## 对总规划的调整（基于本次实现与验证情况）

1. **1b.0c（G3）关闭** —— 路由已修、replay G3 双轮 PASS，从待办移出；
2. **G7-a/b 提到 1b.1"宽池"之前**：宽池解决的是"没有召回池"的问题，而
   G7 的实测主因是"进不了桶/进不了 commit"——先修桶内与 commit 更直接、
   可在当前包上快速验证；
3. **声明词表更新与重建解耦**：`anchoring-declaration` 的 pack 溯源字段
   为元数据（运行时只对 schema/shape fail-closed），词表改动按"配置数据"
   更新并重算溯源，不等重建；
4. **C1 重建窗口合并**：alias batch1b（重建）与可选的"tech_tag 词法归一化"
   （构建侧把自由文本标签派生成规范类目词）评估合并为**同一次重建**；
   是否做归一化由 G7-a 后跨类目离线表现决定——查询侧已稳就不做（避免多一层
   数据变换）。**归一化必要性实测（2026-09-13）**：包内 tech_tags 有
   5,485/7,089（77%）公司携带，但 **4,945 个不同字符串**（最常见仅 17 次），
   2,771 个以"研发商/制造商/服务商"结尾——它不是受控标签，是源表
   `business` 字段的自由文本业务描述一对一搬入（优必选源值＝
   「人形智能机器人研发商」，与包内一致）。类目匹配目前架在这种自由文本上
   （子串/bigram 近似），是"类目查不准"的数据侧根源；若 G7-a 查询侧修法
   跨类目仍不稳，归一化（自由文本 → 受控类目词）随重建执行；
5. **验证顺序**：G7-a/b 当前包先验（重启级成本）→ C1 重建（别名[+标签]）→
   新包上重跑 G7 探针 + 7 会话 replay + g2/g5 抽查——一次重建只做一轮总验；
6. **验收加"本地证明"**：答案中的优必选必须伴随本地 commit/本地证据，
   不允许 web 顺带提及算过（r1/r3 就是这类掩盖）；
7. **lexical 道 ON / rerank ON 的默认开启不放宽**：仍以 1b.3 超集（召回轴 +
   commit 轴）+ 1b.4 四门为闸；
8. **回归卫生**：data-rebuild 发现的环境类红（DB migration revision）加入
   已知清单，与 5 个既有失败、build 停滞文件同账管理。

## 验收定义（G7 算修好的标准）

1. replay G7 重复 3/3：答案含"优必选"，且伴随**本地数字证据**（commit 或
   本地引用），web 顺带提及不算；
2. 诊断脚本：窗口召回 ≥3/3；召回在窗时 commit 3/3；
3. 同族查询（人形机器人/机器人公司）龙头不缺席，泛化样本不回归；
4. g2/g5 枚举回合与 TTFT（<30s）不回归。

## 为什么不是"调参就完了"

把「具身智能」的乘数一调了事会同时放大上千家 "人工智能→智能" 命中——窗口
挤得更满、泛化更差。本次修法走"证据分层 + 平局按证据丰富度 + commit 通道
解耦"，对每个类目查询都生效，且全部确定性、可单测。
