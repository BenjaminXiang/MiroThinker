**质量四轴（用户 2026-09-10 追加裁定）**：**准**（检索准确、事实/立场正确）、**快**（响应速度，每切片记录时延证据）、**全**（枚举与覆盖完整）、**好**（答案质量与可读性）——系统好不好以这四轴衡量，每个切片的验证证据按四轴更新。

**架构原则（用户 2026-09-10 重申）**：本地知识库是精准、快速的第一数据源——离线数据清洗让数据更准更好查；**本地优先，web search+fetch 只作信息补全与事实性补全**。本地命中率与 **TTFT** 是「准」「快」两轴的核心指标；缺口修复方向以此为准（本地可达的优先走本地，web 是兜底不是主路）。

**18188 的角色（用户 2026-09-10 厘清并修正）**：它是用户做 E2E 验证的入口，**最终也是验收对象**——缺口补完的里程碑要在 18188 上启动，供用户亲自体验验证。运行政策不变：当前 18188 的效果不构成切片约束；切片过门即上线（例行操作，保留回滚资产），不再作为生产事件等待确认。交付形态的最终验收对象是「交付包 + 四轴证据」，而 18188 是用户验证体验的落点。

## 1. "功能完备"的验收定义（P1 出口）

1. **需求矩阵全绿**：把需求树 L0–L8（68 条）逐条落成判定项，每条给「满足 / 有据缺口 / 非目标（需用户裁定）」+ 证据（代码路径 / 数据实测 / 端点实测）；
2. **测试集三层判定通过**：实体覆盖 + 立场一致 + 完整性 ≥80%，**25/25**；
3. **覆盖边界通过**：7 类未覆盖需求（专利→企业、教授→专利、类型 D 聚合、话题切换、时效性、超范围拒答、长枚举）各有用例与结论；
4. **数据地基达标**：字段质量阈值（占位/套话/别名/结构化）+ 关系可达 + 数据版本对齐；
5. **16 缺口清零**或明确列入非目标；
6. **本地库可周期更新**（用户 2026-09-10 追加）：能从数据源重建本地库并安全上线——版本化数据包 + 脚本化「重建→封印→切换→回滚」流程 + 更新手册；更新演练（换一版包 + 回滚一次）成功。

> 判定纪律：只看证据，不看文档自述；关键词命中不算通过（GAP-10 教训）。

## 5. 贯穿：系统完善（复杂度治理）

> **用户裁定 2026-09-11**：「证据优先」的本质是**查得准**——保留；「一切可证明」是**过度设计**——系统性修复。用户要的系统：**准确、全面、快速**，且信息**逐步引导**（用户常带着模糊的问题来）。8-21 冻结令升级为执行：**冻结不再新增 → 清点 → 解耦 → 删减**。

**「证据优先」的用户定义（2026-09-11 再定义，取代此前的证明链解释）**：
① **入库质量门**（本地知识库）——采集/整理阶段保证入库数据**准确、精简、干净、结构良好、便于检索**；本地数据的"取证"在**入库时**完成，不在服务期重复做；
② **web 侧质量**——search+fetch 数据经 **LLM 综合判断 / rerank** 筛选；
③ **判据**：**进入 LLM 组稿前的数据是良好的**，即满足"证据优先"。
服务期的证明链（深复现哈希等）**不属于**该定义——归 S2/S3 清退范围。

**证据底线（保留三件）**：① 工件完整性（pack/manifest 文件哈希、marker）；② 版本绑定（release_id/target）；③ 源可追溯（"尽量能指出处"级：citations / 证据 id）。
**设计复核（2026-09-11，按新框架逐类裁定）——「核心保留、四类重做、两项新设计」**

**保留（经 C2 实战检验，不动）**：
- pack + 加载器核心（工件完整性 + 版本绑定 fail-closed）——拦下半封印包等四类真实故障；
- 本地优先车道/检索架构；web 侧门 + rerank（层②据此定义为正解，F3 是修误伤不是拆）；
- 多轮会话机制（收窄/指代/展示集）；三层判定验收体系。

**重做（已在队列，按序）**：
- **S2 服务线解耦**：启动期深复现证明 → 封印期（新定义的直接要求；boot 期 1.75GB 冗余哈希一并处置）；
- **S3 删减**：包内字节拷贝、零读者哈希、`*_isolated` 双份模块的死路径评估（服务只跑 pack 路径后，被隔离实验留下的重复实现可删）；
- **验收口径扩展**：「快」= TTFT p50/p95 入正式证据（不再只看 elapsed）；「逐步引导」= 澄清选项/建议追问用例化判定（现常为空）；
- **需求矩阵复核**：按 8-21 + 9-11 两次裁定，把"完整证明/审计"类条目降为非目标或改写。

**新设计（需立项）**：
- **两线契约家规（single contract home）**：数据线与 serving 线各自演化是 C2 四道门的**总根源**——需一个 ADR 决定：合并为一线，或共享契约模块 + 封印器当唯一闸门（漂移即拒封已具备，缺"契约唯一源"）。**这是 C6 周期更新能否轻量的前提**。
- **入库质量门（C1 扩展）**：字段阈值 + 可检索性 + **入库即检（gate-at-import）**——把"取证在入库"从原则落成机制（发布对账脚本 + 阈值失败即拒绝入库）。

**执行序列（2026-09-11 定位）**：B3+B2 验收 → 两线契约家规 ADR（主上下文起草）→ S2 解耦 → S3 删减；验收口径扩展（TTFT/引导）随各切片证据落账；入库质量门并入 C1；其余队列不变。

**系统性清退对象**：① 通用复现证明（request/result 深复现链——C2 四道门的摩擦源；按用户定义应移至封印期）；② 哈希套哈希的链式放大；③ 为证明而证明的构建/审计机制（说不清拦什么故障的一律进清单）。
**TTFT 联动**：本地数据入库即已取证 → 检索期零证明开销 + 快速命中 → TTFT 提升（与 F1 类目召回、S3 删 boot 期冗余哈希同向）。
**新代码规则**：缺口补齐期间任何切片**禁止新增证明层机制**；新功能走 boring 路径。

| 切片 | 内容 | 验收 |
|---|---|---|
| S1 证明层清点 | ✅ **哈希审计完成**（`.agents/runs/close-workbook-gaps/hash-audit.md`：serving/pack/release 全路径逐项判定；两处零读者哈希、一处 boot 期 1.75GB 冗余哈希、链式放大实测量化、同值重复清单）。全证明层扩展并入 S2 前置 | 清单可审 ✅；"防什么/是否拦过真实故障"逐项在案 ✅ |
