## 1. 现状盘点（规划依据，2026-09-07 核实）

### 1.1 配置面：现网没有配置页面

- 现网有效前端 = V2 后端自带静态页四件套：`/chat`（流式对话，参考前端）、`/browse`（数据浏览+纠错+文档上传）、`/logs`（访问日志）、`/review`（评审台，独立端口 18189）。来源：`apps/admin-console/backend/main.py`（canonical-v2-only 壳，catch-all 将其余 `/api/*` 404）。
- 旧 React SPA 整体断开：V2 壳不挂载 `frontend/dist`，SPA 依赖的 12 个旧 router（`/api/seeds`、`/api/pipeline`、`/api/dashboard`、`/api/upload` 等）现网全部 404。
- 全系统配置无 Web 入口：数据库连接（`DATABASE_URL` / `CANONICAL_V2_*`）、provider key（Bocha/Serper/OpenAlex/S2/本地 LLM，env + 仓库根 key 文件）、模型 profile（profile 表硬钉 + embedding/rerank 两处硬编码默认值——迁移计划第 5 步已指出）、采集行为（概念不存在）。改配置 = 登机器改文件重启；key 配没配、还能不能用，无任何可见性。
- 已知缺陷：`GET /api/canonical-v2/admin/status` 直连 500（deploy/README 记录）。

### 1.2 数据管理操作面：/browse 只承接了一小半

`/browse` 能做：浏览/详情/关联/facets/导出、字段纠错、手工新增、企业文档上传。**无任何入口**的能力（D3 定案全量承接，见 §4）：四域批量编辑/删除/质量标记、XLSX 上传导入（企业→自动富化批次链）、教授 seed 管理（CRUD+触发）、导入任务运维（Milvus 回填/检索验证）、质量问题管理（PipelineIssues）、教授工作台动作（confirm_ready / send_to_review / flag_recrawl）、数据总览 Dashboard。

### 1.3 数据更新：能力齐全、调度为零、发布是一次性冻结

- 四域采集脚本齐全且大多幂等/可断点（企业富化批次状态机 + pg advisory lock、论文 `--resume`/前向单调晋升、上传 hash 去重 + dry-run）。
- 唯一调度器 seed_cron（APScheduler 教授月度重抓）在 V2 壳上无调用方，已失联；OS cron 只有备份（03:17）与日志清理（03:41）。
- **关键断点**：线上 serving pack（`/var/tmp/mirothinker-canonical-v2-s12f/serving-pack/`）是冻结证据一次性构建；新采集数据只进域库（Postgres + 域 milvus.db），要经"release 产物 → manifest 钉 hash → KnowledgeBuild → 索引投影 → build_serving_pack"整条重型链才可被 `/chat` 检索。corrections 持续累积但"下次构建"无流程、无节奏、无一键化。
- 硬阻塞：Milvus Lite 2.5.1 close 死锁影响重建收尾；`admin/status` 500。

### 1.4 用户会话审计：已有半个审计页，缺审计维度（2026-09-07 核实）

- **已有**：`/logs`（logs.html）+ `/api/canonical-v2/admin/access-logs`——会话列表（首问预览/轮次数/状态/时间）、**按提问内容搜索**、状态过滤、分页；会话详情**逐轮回放**（问题原文、回答、引用来源、建议追问、错误详情、耗时）。记录在 chat 流式端点内完成，fail-open（记录失败不影响对话）。数据独立存 `access-logs.sqlite3`（sessions/turns 两张表，turns 含 query_type），每日 03:41 按 90 天滚动清理，且在每日备份范围内。
- **缺口**（对照"审计"要求，D5 定案补齐）：
  1. 无用户身份维度：schema 不记 X-Remote-User（管理区可识别），公开区用户只剩 session_id，无法回答"谁在问"；
  2. 无时间范围过滤（`turns.started_at` 有索引但 API/页面未暴露）；query_type（A–G）存了但不可筛；
  3. 无导出（CSV/JSONL），无法离线分析/汇报；
  4. 无概览统计（每日会话/轮次、query_type 分布、错误率、Top 提问）——而这些数据都在库里；
  5. 保留期 90 天硬编码在清理脚本，页面不可见、不可配置。

### 1.5 部署与运维

- 现网：systemd 用户级 unit + dbg21 nginx 反代（`/guoxian` 公开区 / 管理区 auth_basic + `X-Remote-User`）+ 18188 iptables 收口。
- 客户现场迁移（2026-08-14 计划）：目标机**无 PG**（"PG 只在构建期用"）、总策略"原样搬运运行态、不重建索引"；第 6–10 步（密钥启动/首启冒烟/反代发布/**守护与日常运维**/回退验收）从未产出——本规划是其第 9 步的素材。
- 无告警（失败只有本地日志）；恢复流程手动且未演练。

## 2. 目标与总原则

**目标**：交付后，运维/运营人员**不登机器**即可完成闭环——

```
看状态（pack版本/存储/key健康） → 改配置（采集开关/配额）
  → 管数据（上传XLSX/管seed/处理质量问题/工作台动作）
  → 触发并查看采集任务 → 一键发布新数据包（过门禁、可回滚）
  → 审计用户提问（谁在问/问了什么/答得如何）
```

**原则**：

1. boring、可 inspect：调度用 OS cron + 现有幂等脚本 + 状态落库，不引入 Celery/新框架；页面用与 `/browse` 同体系的静态页，不引入新前端栈。
2. 敏感 key 不进明文 UI：key 管理仍是 env/key 文件，页面只做状态与健康检查。
3. 发布必须过门禁：备份门禁 + replay 回放套件 + dogfood，自动化不得绕过；切换需人工确认（D1）。
4. **管道可分离（D4）**：采集构建段（依赖 PG + Playwright + 域 Milvus）与发布消费段（serving pack + 侧车 SQLite）的 API/页面分开挂载；依赖 PG 的运维 API 启动探测，PG 不可用时降级（端点 503 + 页面入口隐藏），保证现场薄部署不炸。
5. 每片独立可验收、可回滚；行为变更走 OpenSpec。

### 3.2 配置中心内容（MVP）

**（a）系统状态面板**（只读）：serving pack manifest 版本/发布时间/绑定 release_id/hash 校验；**各域数据新鲜度——上次成功采集时间与距今间隔**（取 pipeline_run 历史最晚成功记录）与当前 pack 构建时间并排展示；lookup.sqlite3 与 milvus.db 健康、行数概况；corrections 与 manual-recall 计数；磁盘余量；keepwarm/会话缓存状态。数据源 = 修复后的 `/api/canonical-v2/admin/system-status`。

**（b）采集与调度配置**（可写，进受管配置存储）：各域采集开关（professor/company/paper/patent 分开）；每轮配额上限（web search / LLM 调用次数）与执行窗口（如 01:00–06:00）。

**（c）Provider / 模型 key 状态**（只读 + 健康检查）：每个 provider 展示是否已配置（env/key 文件）、key 尾号 4 位、最近健康检查结果；"立即检查"按钮对各发一次最小探测。**不提供明文查看或 Web 编辑**。

**（d）任务运行面**（与线 B 共用，§5.2）：调度任务清单与下次运行时间、历史运行（成功/失败/耗时/条数）、失败样例入口、**按任务"立即采集"按钮**——与周期任务同一闸门（防重入锁/配额/熔断），手动触发不绕过任何限制。

### 3.3 配置存储与生效

- 新增受管配置存储：serving 侧 SQLite（与 corrections.sqlite3 同目录同模式），key-value settings 表 + audit 表（谁[X-Remote-User]/何时/改了什么）。非敏感、白名单字段才可写。
- 生效方式：采集脚本每轮启动时读取（自然生效）；服务自身行为仍由 env 决定——配置中心只管"数据运维配置"，不出现第二套真相源。
- API：`GET/PATCH /api/canonical-v2/admin/config`、`GET /api/canonical-v2/admin/system-status`、`POST /api/canonical-v2/admin/providers/health-check`。

### 3.4 安全边界

- 全部新页面与 API 置于 nginx 管理区（auth_basic），不暴露给 `/guoxian` 公开区。
- jobs/upload 触发 API 只允许白名单命令，参数固定、不接受任意 shell；audit 记录所有写操作；key 明文永不回显、不落日志。

## 4. 线 C：数据管理操作面承接（D3 全量）

承接原则：**复用旧 API 的业务逻辑（upload/seeds/pipeline/issues 域模块与脚本仍在），以 V2 路由受限重挂 + 静态页重建入口**；不迁移 React 组件，不重写采集链。

| # | 能力 | 承接方式 | 关键依赖/风险 |
|---|---|---|---|
| C1 | XLSX 上传导入 | 旧 `upload.py` 链（hash 去重 + advisory lock + dry-run + 企业自动富化批次调度 + 专利进程内导入 + 教授 pipeline_v3）以 V2 路由重挂，域白名单 company/patent/professor；`upload.html` 承接上传+任务状态轮询+批次详情（旧 CompanyEnrichmentBatch 页核心） | 旧链 subprocess 调 `uv run scripts/...`，需验证 V2 壳进程环境（env 传递、工作目录）——**W3 首个技术验证点** |
| C2 | 教授 seed 管理 | `professor_seed` 表 CRUD + 触发抓取（full/sample/preview）+ 运行轮询，V2 路由重挂；`seeds.html` | 依赖域库 PG（采集段 API，按 §2 原则 4 降级设计） |
| C3 | 任务运维 + 质量问题 | 任务运维动作（Milvus 回填、检索验证）并入 W2 的 jobs 白名单；`issues.html` 承接 PipelineIssues（列表/解决/源行预览） | jobs subprocess 白名单（W2 基建） |
| C4 | 教授工作台动作 | `/browse` 教授详情页增加 confirm_ready / send_to_review / flag_recrawl 按钮，V2 路由承接；send_to_review 后与 `/review` 评审台衔接 | 动作语义与评审台流程对齐 |

**SPA 退役**：C1–C4 完成（W4 验收）后，`frontend/` 归档（标注 deprecated），nginx 5180 代理与 deploy 脚本引用同步摘除——P9 正式收口。

## 5. 线 B：数据周期更新流水线

### 5.1 三层更新模型

| 层 | 内容 | 时效 | 现状 |
|---|---|---|---|
| L1 即时旁路 | corrections（纠错）、manual-recall（手工记录/文档上传） | 即时/下次构建 | 已有，不动 |
| L2 周期采集 | cron 触发各域幂等采集脚本，更新域库 | 周级（D1） | 本规划补齐（W6） |
| L3 周期发布 | 重建 serving pack → 门禁 → 原子切换 → 重启 | 月度一键（D1） | 本规划半自动化（W7） |

### 5.2 调度方案

- 执行载体 = OS cron（声明式表 `deploy/cron/mirothinker-collect` + install 脚本安装），每条 = 现有幂等 CLI 脚本 + `flock`/pg advisory lock 防重入 + 运行记录落 pipeline_run 表（已有）。
- 节奏不进 UI（cron 表写死，改节奏走变更流程重装）；配置中心可调开关与配额（脚本启动时读，开关关闭则空跑退出）。
- 失败可见性：运行状态写库，任务面板红点；连续 2 轮失败自动熔断（disable + 标红），避免配额空烧。

### 5.3 各域采集节奏与脚本白名单（默认值，随 D1 定案）

| 域 | 周期任务 | 脚本 | 节奏 | 配额敏感度 |
|---|---|---|---|---|
| 企业 | 新闻采集（iyiou/36kr/serper） | `run_company_news_ingest.py` | 每周一 02:00 | 高（web search） |
| 企业 | 官网产品重抓 | `run_company_official_product_capture.py` | 每周一 03:30 | 中 |
| 论文 | 无标识符论文标题检索回填 | `run_paper_search_backfill.py` | 每周三 02:00 | 中（学术 API） |
| 论文 | 摘要中文/DOI 回填 | `run_paper_summary_zh_backfill.py` / `run_paper_doi_verify.py` | 每周三 03:30 | 中（LLM） |
| 教授 | 主页重爬（bio/raw text） | `run_profile_bio_rescrape.py`（全量重采按需手动） | 每月 1 日 02:00 | 高（爬虫+LLM） |
| 教授 | 主页论文/专利增量 ingest | `run_homepage_paper_ingest.py --resume` | 每月 1 日 03:00 | 中 |
| 专利 | 无外部 API | 跟随教授主页 ingest + XLSX 手动上传（C1） | 月级/手动 | — |

入表前提：脚本幂等或断点续跑（均满足）；每次运行受配置中心开关 + 配额上限约束。

### 5.4 发布流水线 L3（月度一键，人工确认切换）

```
build_s12f（构建 + dogfood 自举校验）
  → replay 回放套件（replay_fix_round1.py，热更新门禁）
  → 备份门禁（require_accepted_backup_gate，已有，fail-closed）
  → symlink 原子切换 serving-pack 目录 → systemd restart canonical-v2-backend
  → 冒烟（/api/health + 3 条固定问答）
  → 失败自动回切旧 pack 并重启
```

- 触发：配置中心**"立即发布"按钮**或 CLI；**切换前人工确认**（D1）；建议每月一次，与教授月度采集对齐。
- 跑满 2–3 次无人工干预失败后再评估全自动。
- 前置：Milvus Lite close 死锁修复（P0 切片）；`admin/status` 500 修复（随 W1）。

### 5.5 成本护栏

- 每脚本每轮 max calls（web search / LLM 分类计数），超限即本轮终止并标 partial；全部任务限夜间窗口；月度配额汇总进系统状态面板；连续 2 轮失败熔断。

## 6. 实施路线（切片 · 每片独立验收）

依赖顺序：W1 → W2 →（W3、W4、W5 可并行）→ W6 → W7 → W8；**P0（Milvus 死锁）独立，建议最先启动**，否则 W7 被阻塞。W5（会话审计）不依赖 W1/W2，可与 W1 并行启动。

| 切片 | 内容 | 验收线（counts as fixed） | 回滚 |
|---|---|---|---|
| P0 Milvus 死锁前置 | 修复/确认规避 Milvus Lite 2.5.1 close 死锁 | 一次完整构建收尾不挂（构建脚本端到端跑通） | 独立修复，常规回滚 |

## 7. 风险与依赖

- **Milvus Lite close 死锁**（P0，W7 硬前置）：未解决则发布流水线收尾必挂。
- **旧链环境适配**（W3 首个验证点）：upload→pipeline 的 subprocess 链（`uv run`、env 传递、工作目录）在 V2 壳进程内未验证过。
- **PG 依赖降级设计**（D4）：采集段 API 在无 PG 环境必须优雅降级，不能让现场薄部署启动失败。
- **配额费用**：周期化后 web search/LLM 变常态支出，靠 §5.5 护栏 + 面板可见性控制。
- **SPA 退役引用清理**：nginx conf、deploy 脚本、文档中 5180/SPA 引用需同步摘除，防留死链。
- **会话审计两点（W5）**：① access-logs.sqlite3 在线加列属低风险增量迁移，但需对老库验证无损（fail-open 记录链不受影响）；② 提问原文属用户敏感数据，页面/导出仅在管理区 auth 后开放，且默认不记 IP（D5 隐私最小化）。
- **OpenSpec**：P0、W1–W7 均行为/契约面变更，各片动代码前建对应 change（Lite/Standard）。
