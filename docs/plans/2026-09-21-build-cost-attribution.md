1. **landing + 身份解析 ≈ 2h54m**
2. **四域投影（F3 后）≈ 2h03m**
3. **信封序列化 ≈ 1h**（外加索引段 40m、关系投影 38m）

## 3. 这三块的"病"是同一个

- **身份解析段**：成本分析 §3 的三份 py-spy 抓栈（跨两个进程、跨 35 分钟完全一致）指向
  `validate_request` → pydantic `__init__` → `_map_public_authority` → `_logical_graph`
  ——**建图 + 逐对象校验**。
- **信封序列化（≈1h）**：把整棵图 dump 成 7.8 GB 规范 JSON。
- **封印侧解析（33min）**：把同一份 7.8 GB 解析回模型——**这是同一次往返的另一半**。

也就是说：**构建期把图建成模型 → 序列化成 7.8 GB JSON → 封印期再解析回模型 → 再序列化进包（3.3 GB）。**
同一棵图，被 pydantic 走了**四遍**（建、dump、parse、dump）。

今天量到的定标数字（封印侧，直接测量）：**同一份 7.8 GB，`json.loads` 66.5 s，pydantic 解析 1953 s——29 倍。**

## 4. 该做什么、不该做什么

**不该做**：继续优化封印（41 分钟，占 7.9%，上一份归因已下结论）。

**该做**（按收益排序）：

1. **让构建期的阶段计时变成常态**（小改动、收益立即）：本次归因只能靠"run14 的落库时间戳 + F3 的实验室数字"倒推，
   因为 run16 的逐阶段计时**没采到**。构建脚本应当像封印器那样打印
   `phase=<name> seconds=<n>`（landing / identity / projections / relationship / index / envelope），
   下一个 run 的归因就是**零成本**的。**这是下一步最该做的一件事。**
2. **拆掉"信封往返"**（约 2.5 小时的往返里，构建侧 ~1h + 封印侧 33min）：
   封印真正需要的是那几份文档（relationships / catalog），
   让构建期**直接把文档交给封印**、或让封印只构造它要用的那几块，都能省掉一次全量 dump+parse。
   这属于 `reduce-rebuild-validation-cost` step 2 的"contract slimming"，**需要 OpenSpec 级的契约决定**。
3. **四域投影段的 2h03m**：S1 之后是否还有同类"逐行校验"，要等第 1 项把计时装上去才能判断。

## 5. 与 R12（周期更新）的关系

R12 说"先做全量重建的 boring 流程（正确优先）"。当前的 boring 流程 = **构建 8h + 封印 41min + 切包 291s**。
用户可见的"更新一次"成本因此是 **~9 小时**，其中构建占 **89%**、封印 7.6%、切包 0.9%。

**结论：周更不痛的关键在构建，不在封印，也不在切包——而后两者的账已经还完了。**
