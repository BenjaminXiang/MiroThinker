# 别名闭包规划：让「字节跳动」对上 ByteDance Ltd.（2026-09-13）

> 定位：C1 数据治理切片（change-id `close-workbook-gaps`，C1.1-batch1）。
> 关联执行日志：`2026-09-10-system-completion-log.md` 条目 36/37。

## 问题（一句话）

用户在系统里问「字节跳动」，系统找不到这家公司——本地库里明明有
`ByteDance Ltd.`（产品、行业、团队齐全），但它没有任何中文品牌名别名，
检索只能命中"顺带提到字节跳动的其他公司"。

## 根因（已实测）

- 包内 7,089 家公司里只有 **342 家（4.8%）** 有别名；ByteDance 的别名字段为空。
- 数据源 `p4-company-full-v1.jsonl` 里 **6,504/6,514（99.8%）** 家公司带
  `project_name`（品牌名），ByteDance 那行就是「字节跳动」——数据一直在，
  但构建链没有任何代码把它写进别名。
- 检索侧别名匹配（全名/别名/短名通道 + 唯一性守卫 + 扇出上限）早就实现且
  是 fail-safe 的（歧义时不绑定、回退正常检索）——缺的是数据，不是算法。

**结论：在数据治理层（构建侧）解决；不做查询侧模糊联想。**

## 怎么修（已完成一半）

**已做（batch1a，代码 + 干跑，未上线）**

- 构建侧把 `project_name` 投进公司别名：新公司进 `core_facts.aliases`，
  存量公司走字段合并的**并集**（去重、剔除与公司全名相同的形态）；
- 护栏沿用检索侧既有机制（泛词误绑由唯一性判定兜底，不新建词表）；
- 单测 7 条（RED→GREEN）；全量干跑（复用真实构建函数）实测：
  - 新增别名 **6,504** 条 → 覆盖率 **4.8% → 96.6%**（342 → 6,846 家）；
  - 冲突形态仅 **9 个**（各涉及 2 家公司，如「乐聚机器人」→ 乐聚两家关联
    公司），均在检索侧安全阈值内：保留 + 报表，歧义时系统会回退而不是乱绑；
  - 对回填批次的身份匹配副作用：**0 条**（逐一验证 700 条记录）。

**待做（batch1b，重建与验收）**

1. 全量重建候选 → 打包 → 封印（沿用既有 boring 重建流程）；
2. 把 18188 切到新包（旧包保留，回退=指针切回 + 重启）；
3. 验收探针：
   - 「字节跳动」→ 命中 ByteDance Ltd.（本地别名通道）；
   - 「优必选」等既有查询不回归；
   - 冲突形态（如「乐聚机器人」）不误绑、走歧义回退；
   - 7 会话 replay 门 + g2/g5 测试集抽查。

## 验收定义（这件事算完成的标准）

1. 重建后包内「字节跳动」→ ByteDance Ltd. 可直接命中；
2. 别名覆盖率 ≥ 90%（预计 96.6%），且冲突/自名形态报表在案；
3. replay 门与既有测试集不回归；
4. 回退路径演练过一次（指针切回旧包）。

## 为什么不是查询侧修

查询侧做模糊/语义联想是补丁：无法知道「字节跳动 = ByteDance Ltd.」这类
实体事实，只能靠模型猜；构建侧把品牌名固化成数据后，所有查询通道
（精确点名、多轮追问、专利/公司遍历）一次性受益。本地确实没有的实体，
继续走 web 补全——两条路分工不变。
