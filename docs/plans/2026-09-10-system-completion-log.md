## 2026-09-10 · 条目 2：B1 第一轮——移植成功但不可达，设计修订；A4 流量证据

### 做了什么

1. **B1 第一轮**：数据线的企业→专利直扫块移植到部署线（commit `b20161d`，+79 行），
   并补了一道源块缺失的路径资格护栏（同一缺陷在数据线同样存在，已记回植欠账）。
2. **设计修订**（B1 第二轮开工）：第一轮证据发现直扫块在当前服务包上**根本不会被调用**，
   上游两道闸门把它挡死了。修订已落入 OpenSpec 设计文档，第二轮由同一执行者继续。
3. **A4 真实流量出包率**：访问日志 751 轮 × 两个数据包名称池，跑完了覆盖对比与流量形态分析。

### 发现

- **闸门 A（绑定层）**：「优必选有哪些专利」这句话绑不上优必选公司——匹配模式只认"X的专利"
  （不认"X有哪些专利"），且包里别名没有裸"优必选"短名。→ 修订：补语形 + 派生短名通道
  （剥"深圳市…股份有限公司"前后缀，唯一性守卫防误绑）。
- **闸门 B（分发层）**：当前包没有逐边资格行，企业→专利查询全部被分发到只扫关系表的路径
  （关系表 121 行/48 家，不含优必选）；移植块所在的函数因此不会执行。正对照：普渡同名查询
  返回 17 个候选——车道机械正常，是分发+数据形态问题。→ 修订：直扫改挂到实际执行的路径上，
  两路共享同一辅助函数。
- **引用层**：普渡探针 17 个本地候选仍然 citations=0——本地引用不上浮是独立缺口（B1c/B4）。
- **重放门抖动**：同一代码 3 次重放 7/7、6/7、6/7，失败子集互不相同，且所有失败签名在
  历史未改动代码的日志里反复出现——判定为 LLM 渲染抖动（预存问题），已立项治理（A3.4）。
- **流量形态**：真实查询 38.1% 是枚举类（"有哪些"）、32.9% 是追问指代类——**枚举 + 多轮
  才是流量主体**。高频榜第一「深圳有哪些做具身智能的公司」×96 正对应语义枚举缺口；
  「该公司的专利/优必选有哪些专利」合计 37 次正对应 B1。run14 对"点名实体流量"的边际覆盖
  只有 3 条——它的价值在**同一批高频实体的答案深度**，不在解锁新查询。

### 怎么验证

- 闸门 A/B 结论有实时 SSE 探针证据（plan_done 车道列表、retrieval_done 候选数）+
  SQLite 直查（优必选 58 条绑定在包内，函数若可达即可命中）+ 正对照（普渡 17 条）。
- 流量分析脚本与结果归档在 agent 侧 verification 文档，可复跑。

### 影响哪些问题

- GAP-01 修复面从"移植一块"扩为"绑定 + 分发 + 扫描 + 引用"四点，设计已修订。
- B2/B3（枚举与收窄）被流量证据确认为最高频缺口，排序不变。
- C2（run14 上线）价值重述：提升答案深度，不是解锁新查询；优先级不变（B 先 C 后）。

### 下一步

- B1 第二轮（闸门 A/B + relationship 道引用上浮）执行中，GREEN 标准：g17-t1 三层全过 +
  普渡正对照不回退 + 重放门无新失败签名。

## 2026-09-10 · 条目 3：B1 完成——三闸门串联修复，g17-t1 三层全绿，GAP-01 关闭

### 做了什么

1. **B1 第二、三轮完成**（执行：agent-4；设计修订 + 机制逐行核实：主上下文）：
   - 闸门 A（绑定层）：派生短名通道让「优必选有哪些专利」绑上公司锚点
     （company-c-64e631c0e0cd9e91d032d209）。原计划的"所有格模式扩展"被合理跳过——
     短名通道已覆盖该语形，且扩展会误触发「…的竞争对手有哪些专利」。
   - 闸门 B（分发层）：直扫辅助函数 `_direct_patent_applicant_scan` 挂到实际执行的
     源绑定路径，优必选得 48 个候选（58 条绑定 − 10 条被路径资格护栏排除）。
   - 闸门 C（约束层，第二轮后才显形）：约束层的"展示集见证"此前只认关系 trace，
     直扫证据项按设计不带 trace → 48 个候选全部被 displayed_entity_set 槽硬拒。
     修法：新增绑定见证分支，与答案选择器已有的 `_claim_binding_binds_anchor`
     严格同语义（relationship 道限定、trace 分支优先、只看绑定 value 端、
     绑定须关于候选自身），并加两侧等价契约测试防漂移。
   - 引用层：无 URL 的本地关系证据现在发 `local-source-<sha>` 本地引用卡。

### 发现

- 这道缺口实际是**四层串联**（绑定 → 分发 → 扫描 → 约束），修通一层下一层才显形；
  每层的 RED 都给出了更精确的位置，没有返工。
- 约束层的根因是「约束门比下游选择器更严」：选择器早已按同语义放行这类候选，
  约束层却先一步拦截，答案根本没机会生成。教训：**同语义判定必须单一实现或
  等价锁定**——本次用契约测试把两处钉在一起。
- 修复后答案诚实披露规模：「共检索到 48 件相关专利，此处列出部分示例」，
  附 16 张本地引用卡；不再依赖天眼查网页。

### 怎么验证

- 新增测试 3 个（先 RED 后 GREEN）：正向过闸 ×1；负向不误放 ×4（跨锚 value /
  subject 端朝向 / 非 canonical 值 / 非 relationship 道）；选择器等价契约 ×1
  （5 例矩阵）。夹具来源：按直扫实际发射的证据项形状构造（最小复现脚本翻转
  为 GREEN 护栏）。
- 预存回归：原子约束契约文件 8 passed；聚焦套件 `-k "relationship or patent"`
  96 passed / 26 skipped / 0 failed（与第二轮同数，无回归）。
- 活端点三层判定（新 runner，非快照）：g17-t1 PASS——实体 ✓（优必选）/
  溯源 ✓（16 CN 号 + 16 本地引用）；16 个 CN 号经服务包 SQLite 逐条复核，
  16/16 绑定优必选（含联合申请 CN117559877A）。
- 正对照普渡不回退（17 候选 / 16 CN / 16 本地卡，与第二轮一致）；
  重放门 7/7，历史抖动签名本轮零出现（未动用临时抖动政策）。
- 证据链：agent 侧 verification-b1.md 三轮全录；worktree commit `197b7f5`。

### 影响哪些问题

## 2026-09-10 · 条目 4：B2 取证——GAP-04 的真实门槛是数据深度，建议改道 C2 先行

### 做了什么

1. 开工 B2（收窄缺口）前先做失败层定位：逐层追了 g2-t2/g5-t2 的问句、GT、
   基线答案形态、会话 manifest 机制、两个数据包的企业覆盖与地理字段填充率。

### 发现

- **基线答案形态**：g2-t2 只答出普渡（1/6），且明说优地/云迹"总部未明确披露"——
  优地公司名里就带"深圳"；g5-t2 答"上述两家企业均为深圳企业"（2/12），而 t1
  答案实际展示了 5 家（嘉立创/捷多邦/凡亿/一博/深南电路）。
- **机制缺陷（代码侧，GAP-04 本体）**：会话 manifest（`_displayed_ids`，
  canonical_v2_chat.py:2035）只收 canonical 绑定的实体——web 展示的未绑定公司
  全部掉出收窄全集；收窄轮对未绑定成员没有任何核查路径（连名称含"深圳"都识别
  不出）；答案无覆盖声明，把残缺子集当成完整答案。
- **数据门槛（决定性）**：当前 s12f 包 1,737 家企业，g2 GT-6 只在包 3 家、
  g5 GT-11 只在包 3 家，且**全部企业 geography/registered_address 字段为空**
  （唯一地理信号是名称里的"深圳"）。**run14 包 7,089 家、地理/地址填充 91.9%**：
  g2 GT-6 六家全在且带深圳地址，g5 GT-11 在包 8 家（华秋/中信华/领智/鼎纪缺），
  g2-t1 的五家 GT（含开普勒/九号）全部在包。
- **结论**：g2-t2 ≥80%（≥5/6）和 g5-t2 ≥80%（≥9/11）在当前包上**无论 B2/B3
  怎么做都到不了**——门槛是数据深度，不是代码。这正是用户警示的"用复杂方式
  实现简单需求"的反面教材：在浅包上造精巧机制，断言照样红。
- **C2 可行性**：run14 服务包构件已在 `/var/tmp/mirothinker-data-v2/
  serving-pack-run14/`（lookup 47,071 docs、milvus、relationships 2.9G、
  manifest、index-target 描述文件），C2 = 薄加载上线 + 对账 + 重基线，
  工作量有界。

### 怎么验证

- 两包逐名核对（24+7 个目标公司，含别名匹配）：s12f/run14 各跑一遍
  lookup SQLite 全量扫描，命中情况与字段填充率如上。
