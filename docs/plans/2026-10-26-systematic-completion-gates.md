## 1. 为什么重新排一次序

功能不缺，缺的是**判断什么算完成**。现有三条线（客户现场补齐、标准问答对齐、教授画像闭环）各自都在推进，但共用一套失真的地基：

- 客户机 `100.64.0.96:/root/deploy/fullstack-v2/code` **不是 git 仓库**，10-21 至 10-26 有 31 个 py 文件被改，`run.sh` 被重写；
- 这 31 个文件相对 `switch/embedding-model-to-qwen37-flash`：9 个一致、18 个不同、4 个在该分支根本不存在（只在 10-23 的 `codex/canonical-v2-s12a-ready` 快照里）；
- 本地 `:18188` 与客户机走**同一条启动链**（`serve_s12e_port.py → complete_candidate_runner → import backend.main`），但进程自 10-16 未重启，Python 在启动时就冻结了当时的 import、环境也停在当时（无答案缓存开关）——它验证不了 10-16 之后的行为。这是「进程冻结」，不是「另一个应用」（第 1 轮判断已在第 2 轮更正）；
- `release/customer-test` 停在 8-19，与 AGENTS.md 写的「客户热更新线」已经脱节。

结论：最新行为只活在一台机器的文件系统里，任何重封/换机/重建都会静默回退，且没有测试能发现。

**工作原则（2026-10-26 用户确认）**：客户机是运行时的唯一权威，仓库是它的可复现副本；
任何行为修复先在客户机生效，随后回灌进分支并让漂移检查归零；仓库侧工具（评测、漂移检查）
不部署到客户机。开发方式可以就便，但「客户机代码最完整」这条不能被便利性破坏。

## 2. 四道闸门

```text
闸门 1 可复现  ──→  闸门 2 可度量  ──→  闸门 3 数据竖切  ──→  闸门 4 运行化
（代码归位）        （一条命令出分）      （教授×论文闭环）      （调度+观测+切包）
```

| 闸门 | 目标 | 退出条件 |
|---|---|---|
| 1 可复现 | 部署树 = git 树，漂移可被机器发现 | 回灌分支 + drift 检查 0 差异 + 4 条采纳行为有测试 |
| 2 可度量 | 一条命令给出分数与逐题 diff | `just eval-gate`：27 轮 + 基线对比 + 双分制（exact / product） |
| 3 数据竖切 | 20 位教授端到端打穿 论文→画像→检索 | `paper.professor_ids` ≥60%、模板率 <10%、q27 稳定 |
| 4 运行化 | 采集→画像→pack 的周期刷新 + 观测 | 指标看板 + 定时任务 + 一次计划内切包 |

### 3.6 模板简介清理（2026-10-27）

**问题**：2,149 / 3,958（54.3%）条教授简介含有补位句
「该教授在深圳科创领域有持续贡献。」——它不是证据，是
`pipeline_v2._build_fallback_summary` 为了凑够 200 字符循环追加出来的，
之后进了研究向量，也进了每一条 claim。

**修法（两层）**

1. **源头**：fallback summary 不再补位。短而真实的简介保持短；
   200 字符契约仍用于校验 LLM 产出，不再当作 fallback 的目标。
2. **存量**：claim 渲染时先丢弃已知补位句，再做去重与截断——不用重建 pack
   就能让线上答案立刻干净。

**安全性**：2,149 条里 **0 条**是「纯补位」（去掉补位句后仍有 ≥20 字真实内容），
所以过滤不会把任何 claim 清空。

### 3.10 画像补全的可行性验证（2026-10-27）

重建暂缓后，真正的缺口浮出来：**2,856 位教授只有姓名+机构**。这一轮先验证现成的补全链路能不能补。

**实测（本地 collection DB，5 位薄画像）**

| 结果 | 数量 | 质量 |
|---|---|---|
| 补全成功 | 4 | 摘要 200–253 字、19–23 条已核实事实、抓取 5–9 个页面 |
| 被契约拒绝 | 1 | `profile_summary_too_short` |

抽查补全后的摘要：包含研究方向、著作/论文、获奖、履历——是**真内容**，不是注水。

**关键发现**：`PROFILE_SUMMARY_MIN_CHARS=200` 会把真实摘要拒掉（试点 1/5）。
这正是当年 fallback 补位的动机——为了过 200 字门而注水。

**已修**：下限 200 → **120**（prompt 同步改为 120–300）。教授质量套件 50 条测试全过；
试点里被拒的那位（陈振旺）复跑成功（283 字 / 19 条事实）。注意：单例复跑不能证明因果
（重试也可能产出更长版本），改动依据是试点中 120–190 字这一类的被拒。

**下一步试点设计（20 位）**

1. 选 20 位薄画像（优先用户常问的机构/方向）；
2. 用现有链路补全（DeepSeek 搜索 → 抓页 → 身份校验 → 合成）；
3. 写入客户机的 manual recall（**立即进服务**，不需要重建），带来源 URL；
4. 验收：20 条记录可见、每条 ≥120 字且 ≥10 条事实、抽 3 位提问能答出补全内容并带 citation、
   27 轮评测门不退化；
5. 回滚：manual recall 支持 tombstone，按记录撤销。

### 3.12 客户机 20 位试点执行结果（2026-10-27）

在客户机采集库上真的跑了：导入 20 位薄画像 → 补全 → **17/20 成功**。

| 指标 | 值 |
|---|---|
| 导入 | 20 位教授 + 20 条机构 + 20 个主页页 |
| 补全成功 | **17** |
| 简介长度 | 4–300 字，均值 **208** 字 |
| 已核实事实 | 2–30 条/人；抓页 2–10 个/人 |
| 未成功 | 3 位（1 位报错、2 位无结果） |

**踩到并修掉的坑（重要）**：补全的 UPDATE 只在"新简介比旧的**长**"时才写，
而 SELECT 又要求 `profile_summary IS NOT NULL`。所以：

- 导入 pack 里的补位文本（226 字）→ 真实的 223 字简介**输不掉旧值**；
- 把摘要置 NULL → 教授**选不中**。
