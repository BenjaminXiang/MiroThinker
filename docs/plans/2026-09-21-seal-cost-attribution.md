# 封印侧归因：33 分钟不是"重复证明"，是 pydantic 构造（2026-09-21）

> 类型：分析（为什么问题会发生 · 含一条被自己证伪的假设）· 写一次
> 触发：第 23 轮重封一个包花了 41 分钟，其中 `phase=envelope_validate` **2008 秒（33 分钟）**。
> 我的假设是"又是重复证明"（对 7.8 GB 对象图重算内容哈希）。**实测证伪了**：
> 重算只占 **13.9%**，真正的大头是**把 JSON 变成 pydantic 模型**。

---

## 1. 方法

一次进程内、两段对照（同进程、同文件、同一份代码）：

1. `read_bytes()` 单独计时；
2. `CompleteCandidateBuildEnvelope.model_validate_json(raw, context={"external_content_addressed": True})` 计时——即封印走的真实路径；
3. 把 `_model_sha256` 换成"直接返回对象携带的值"（每条比较因此恒真，但 dump+hash 全部跳过），**再跑一遍同样的校验**。

脚本：`/tmp/boot-prof/seal_attribution.py`（临时物）。

## 2. 结果

| 段 | 秒 | 说明 |
|---|---|---|
| `read_bytes`（7.73 GiB） | **4.5** | 页缓存命中，可忽略 |
| 完整 `model_validate_json` | **1953.3** | 与封印实测的 2008 s 互相印证（差 3%） |
| 同上，但不重算内容哈希 | **1682.6** | 只跳过了 **3 个**内容对象 |
| **重算哈希的占比** | **13.9%（≈271 s）** | 我的假设在这里，只有这么多 |
| 剩下的大头 | **≈1682 s（86%）** | **解析 + 构造模型** |

再补一刀定标：

| 动作 | 秒 |
|---|---|
| `json.loads` 同一份 7.73 GiB | **66.5** |
| pydantic 整包校验 | **1953.3** |

**同一份字节，pydantic 比纯解码慢 29 倍。** 差额（≈1887 s）几乎全是**建模型**：7.8 GB 里成千上万个对象、
每个字段都要走校验与 `__init__`。

## 3. 这条结论推翻了一个方向，并给出了新方向

- **不是**"再算一遍哈希"——那只有 271 s，而且只有 3 个对象（虽然它们巨大）。
- **是**"把图过一遍 pydantic"——信封在**构建期**已经被构造成模型、序列化成 JSON，**封印期又从 JSON 构造回模型**，
  然后写进包里（3.3 GB 的 `relationships.json`）。**7.8 GB 的图，被 pydantic 走了两遍。**
- 真正便宜的做法是让**构建期直接把包的文档交给封印**（或者让封印只构造它真正要用的那几块、
  其余按原始 JSON 携带），而不是"序列化→反序列化→再序列化"。

## 4. 但**先别做**：它在周期更新里只占 7.9%

| 环节 | 耗时 |
|---|---|
| 全量重建（触发器修复后，run16 runbook 口径） | **~8 小时** |
| 封印（本轮实测，含 `envelope_validate` 33 分钟） | **41 分钟** |
| 封印占比 | **7.9%** |

把封印从 41 分钟压到 5 分钟，只能省掉周期更新总成本的约 **7%**。**R12/C6（周更不痛）的瓶颈在构建，不在封印。**
这条归因的价值因此是**负向的**：它明确告诉后续不要把力气花在这里，除非构建成本先降到同一量级。

## 5. 顺带记下的一条通用事实

**pydantic 建模 ≈ 29 × 纯 JSON 解码（同一份 7.8 GB 数据）。** 这条同时解释了启动侧剩下的
authority 构造（A 兑现后仍有约 125 s）与"为什么把 3.3 GB 关系数据在启动期构造成模型这么贵"——
即 R11/P3 里"关系数据惰性/存储化"的真正理由是**别在启动期把图建起来**，而不只是别读它。
