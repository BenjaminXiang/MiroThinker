1需求：系统要解决什么

1.1 业务背景与用户

面向深圳科创生态的对话式科创信息检索系统：用户在网页上用自然语言提问，系统在教授、企业、论文、专利四个数据域中智能路由检索，返回结构化、可追溯（带引用）的回答。典型提问：

  • 「优必选有哪些专利」—— 专利域 + 企业关系 ｜「丁文伯教授的研究方向」—— 教授域（含主页画像）
  • 「详细介绍国先中心（深圳）」—— 机构实体 ｜「深圳有哪些做具身智能的公司」—— 枚举型多实体
  • 「该公司的专利有哪些」/「他有哪些论文」—— 多轮指代（紧随上文） ｜「目前主流的 JEPA 变体有哪些」—— 通识/概念题（本地无料，走 web）

1.4 硬约束（设计时不能违背）

  • 现场无 GPU：一切模型能力（回答/嵌入/重排/搜索）都走外部 API 或本地数据库。设计不得引入本地推理。
  • 内网环境：外网通道受限（见 §7.3 陷阱）；大文件传输要考虑中继/中转策略。
  • 密钥可现场配置：甲方管理员必须能在 web 页面更换 API key（不依赖我们改代码/改文件）；因此密钥走「受管文件」，且不能被环境变量压住。
  • 稳定优先于聪明：冻结校验链 fail-closed；启动慢可以接受（现场 6–11 分钟），启动错不行。
  • 可回滚：任何切换都要有分钟级回退路径（站点/版本/数据三级）。

2.2 数据域与查询路由

  • 四域：教授（professor）/ 企业（company）/ 论文（paper）/ 专利（patent）。每个域有独立的抽取、清洗、归一化模块（src/data_agents/<domain>/）。
  • 查询分类：系统对用户问句做类型判定并决定「走哪些车道、要不要澄清」。在 SSE 与日志里可见的行为分支形如 canonical_v2:A:answer（直接作答）与 canonical_v2:G:clarification_only（缺主体时先澄清、不检索）。完整 A–G 语义以 openspec/specs/ 与共享契约为准（本材料不复制该表，避免过期）。
  • 路由示例：「优必选有哪些专利」→ 专利域 + relationship 车道；「丁文伯教授的研究方向」→ 教授域 exact+structured+语义检索；「JEPA 变体」→ 本地无料 → 纯 web 车道。
  • 多轮指代：紧随上文的「他/她/该公司」由上文的会话主体承接；主体类型不匹配（如对机构说「他」）时走澄清（clarification_only），这是 G3 修复的行为契约，改动需谨慎。

2.3 服务栈与冻结链（这是全系统最需要先理解的部分）

服务进程不连接知识源构建链，只读一份「服务包 + 索引 + 记录式 bundle」的组合；启动时按冻结校验链逐项校验，任何一项不一致直接拒绝启动（fail-closed）。

构件现场路径关键身份
服务包 pack/var/tmp/mirothinker-data-v2/serving-pack-fembed-v1/manifest.json（schema canonical-v2-serving-pack-v2）注册四文件哈希：lookup.sqlite3 / relationships.json / institution_catalog.json / marker；index_root 与 index_forbidden_milvus_paths 以绝对路径冻结
向量索引/var/tmp/mirothinker-data-v2/index-v4-v2/lookup.sqlite3 + vector_matrix.npz + marker；marker sha256 df594dc5…（release candidate-v2-20260922-r1）
记录式 bundle ×3<bundle>/gate-evidence/{s12a,s12c,s12g}/decision bundle（离线判定）/ embedding bundle（模型身份+端点+维度）/ serving bundle（release、DB 名、索引根、envelope 绝对路径、web 预算）——serving bundle 以 content_sha256 钉死
mount receipt…/serving-pack-fembed-v1.mount-receipt.json首次校验通过后写；后续启动凭它跳过全量哈希（只核对 pack_dir/清单哈希/marker/文件首末块指纹）
三条「绝对路径」必须逐字一致（现场迁移时最容易踩）：① pack 清单里的 index_root；② serving bundle 里的 envelope_path；③ 命令行的 --accepted-original-milvus-path。它们指向的是构建机的原路径，现场只需把这些目录建出来（文件本身不必存在）。这也是为什么现场的 run.sh 里能看到 /home/longxiang/… 这样的路径——不是笔误。

2.4 一次问答的生命周期（SSE 事件协议）

前端 /chat 通过 POST /api/chat/stream 拿 SSE，事件顺序（以「优必选有哪些专利」实测为例）：

[ 0.9s] event: stage         name=planning            # 查询理解/规划（会调一次小模型）
[ 1.9s] event: plan_done     lanes=[relationship,web] domains=[patent]
[ 1.9s] event: stage         name=retrieval
[ 7.3s] event: progress      detail="✓ relationship：128 个结果"
[ 7.3s] event: progress      detail="✓ 网络搜索：41 个结果"
[ 7.3s] event: retrieval_done lanes=[…状态与候选数…]
[ 7.3s] event: stage         name=synthesis           # 检索完→合成答案
[ 9.0s] event: answer_chunk  …（流式文本块，可能上千个）
[14.0s] event: answer        answer_text=…            # 完整答案
[14.0s] event: done

时间轴为现场机（Core2）实测。TTFT（用户看到首字）= answer_chunk 的首个事件时间；总时长 = done。看门狗/探针就是按这两个指标采样的。

2.5 管理台与 sidecar

  • 登录：admin-auth.sqlite3（sqlite，非 PG）+ 签名 key + 首启一次性口令文件 var/admin-initial-password.txt（0600）。
  • 密钥页：GET/PATCH /api/canonical-v2/admin/secrets，写入 code/config/managed/secrets.json（原子写 + 0600 + 审计）。改后需重启服务生效（服务仅在启动时读取受管文件）。
  • sidecar（均由环境变量指定路径，默认落在 var/）：访问日志（每轮问答落库）、纠错、人工召回（运营注入的别名/记录，可覆盖默认召回）、chat-gaps（缺口台账）、jobs（采集任务台账）。

2.6 关键设计决策（以及为什么）

决策理由对维护者的含义
知识面与构建面彻底分离（pack 只读）现场不能跑 20 小时重建；服务启动必须确定、可校验改数据 = 我侧重建 + 重封 + 切包；现场只换文件
冻结校验链 fail-closed宁可启动失败，不愿「用错数据悄悄回答」启动报错先怀疑「身份/路径不一致」，不要放宽校验
密钥放受管文件、不进环境变量环境变量优先级高于受管文件，会压住页面配置禁止把 API key 写进 .env 或 unit 的 Environment=
web 车道与向量车道均可降级外部依赖（搜索/嵌入）可能不可用；一个车道失败不应杀整轮检索慢/空先看车道日志与探针，不要动校验链
TTFT 优化：探针到点即返、页面预取重叠用户在意的「慢」主要是首字等待改规划/检索时留意这两处不变量，别退回串行
模型走公有 API（嵌入/回答）现场无 GPU模型身份被 bundle 钉死；换模型 = 重建向量空间 + 重封

3.3 启动链路（逐步，照着读一遍就能自己起服务）

  1. systemd 起服务：现场 miro-fullstack-v2.service → /root/deploy/fullstack-v2/run.sh 18188；开发机是 user unit canonical-v2-backend.service → start-canonical-v2.sh → 命令文件（同样是 run.sh 的等价物）。
  2. run.sh 导出 sidecar 路径、显示档位、PYTHONPATH（admin-console 在前、miroflow-agent 在后），然后调用 .venv/bin/python code/serve-script/serve_s12e_port.py 18188 <全套冻结参数>。
  3. serve_s12e_port.py：把解析到的端口覆写为 18188，再把 sys.path 指向同树 s12a/，委托 complete_candidate_runner.main()。
  4. runner _parse_args() 做启动前校验（看这段就知道每个参数为什么存在）：release↔DB 名绑定、envelope 路径必须等于 gate-root 派生路径、staging≠index、各显式路径互不重叠、parent 目录必须存在等。
  5. main()：--serve-existing + --serving-pack 成立时走包通道（不读 envelope）→ create_serving_pack_handoff → open_serving_pack_authority()：
    • 在这一步调用 apply_managed_runtime_config()——受管设置/密钥在此时投影进进程环境（这也是「改密钥要重启」的原因）；
    • 校验 pack manifest（release / index target / marker / 四文件哈希 / 禁止 Milvus 路径）；
    • 有 receipt 走指纹快路径，否则全量哈希并写 receipt。
  6. _serve()：load_recorded_serving_inputs()（读三个 bundle、校验 content_sha256、装配嵌入适配器与页面抓取器）→ 组合运行时（planner / knowledge_read / answer / sidecars）→ uvicorn.run(backend.main)。
  7. 就绪信号：GET /api/health 返回 200；现场 unit 的 ExecStartPost 随后自动预热 3 题。

排错提示：启动期间 serve.log 会先打印 candidate_release_id=…、serving_pack=…、relationship_request_sha256=…、index_projection_request_sha256=… 四个标记——它们与我方线逐位一致就说明包与重建完全同源，这是排查「现场与我方不一致」的第一对照物。

6开发工作流（动手前必读）

本仓库有明确的纪律文件：AGENTS.md（执行纪律，面向 code agent）与 CLAUDE.md（编排/评审策略）。先读它们，再动代码——下面的摘要不能替代原文。

6.1 纪律摘要（违反任何一条都算这次改动有缺陷）

  • 先立契约再动手：写清 Goal / Expected behavior / Context / Constraints / Done when / Out of scope；并按规模分类（tiny / standard / pattern-fix / risky）。
  • OpenSpec 门：行为类改动（用户可见行为、公开 API/数据契约、业务规则、检索/融合/重排/回答/引用、工具策略、权限、错误语义、验收标准）必须先有 active change（tiny 用 Lite，standard 带 design.md）。没有 change 就停下报告，不要自行发明需求范围。
  • 双文档体系：给人看的在 docs/plans/（index.md 状态板 + 每轮 append-only 日志：做了什么→发现→怎么验证→影响哪些问题）；给 agent 的验证据在 openspec/changes/<id>/ 与 .agents/runs/<id>/。一个切片只有两侧都写齐才算 Accepted。
  • 验证分层：报告必须分 ①本次新增的测试（数量+锁住什么+夹具来源）②既有回归套件（数量+是否全过）③RAG/chat 级证据（replay / 故障注入）。「全部通过」这种笼统数字不合格。
  • RAG/chat/路由/prompt/policy 类改动：单测不算 GREEN——必须跑回归门（replay）与/或召回门。
  • 热更新红线：切到 release/customer-test 或客户现场前，replay_fix_round1.py 必须 7/7 ALL PASS。
  • 最小改动：每一行都要能追溯到任务契约；不做顺手重构；删错逻辑优先于补丁；不为了过测试而放宽校验。
  • 不推上游：origin 只允许 BenjaminXiang/MiroThinker；永远不要推到 MiroMindAI/MiroThinker。

6.4 一次改动的标准流程（示例：修一个检索 bug）

  1. 复现：先写失败的测试或 replay 断言（RED）。写不出来就先把现象固化成探针输出（stage-timing 的逐车道耗时、access-logs 记录）。
  2. 定位层级：UI / 查询理解 / 检索 / 存储 / 数据 / 构建，六选一；分清「用户可见面」与「内部工程对象」——症状在表层不代表修在表层。
  3. 改根因：优先删除产生错误的逻辑；同类问题（pattern-fix）先做兄弟搜索再统一修，别打单点补丁。
  4. 验证：定向单测 + 回归门；若是检索/回答类，还要看召回/引用是否不劣化。
  5. 落文档：docs/plans/ 追加本轮日志 + 更新 index.md 状态。
  6. 上线（仅当需要）：走 §7.1 的「构建→传输→切包→验收」；现场代码不是 git，是文件快照。

6.5 生产禁忌（血泪版，都是本项目真实踩过的）

  • 不要把 API key 放进 .env 或 unit 的 Environment=——环境变量会压住页面配置，导致「甲方改了 key 不生效」。
  • 不要给 0600 文件写裸的 os.chmod(path, 0o600, follow_symlinks=False)——用 backend/private_files.chmod_owner_only()（Python 3.12.13+ 会抛 NotImplementedError）。
  • 不要改 pack/index/bundle 的任何身份字段（release、marker、content_sha256）——那是冻结链。
  • 不要在现场机上动 run-9 目录、宝塔、MySQL、防御 agent。
  • 不要假设现场能直连 Fastly/GitHub 资产/任意 registry——先看 §7.3。

打包范式（本次迁移实证，可照抄）

# 1) staging：代码树 rsync（排除 .venv/__pycache__/.agents 等）+ 大文件用 cp -al 硬链接（零拷贝）

# 5) 自检：install-v2.sh 内置 12 项哈希校验（bundle 文件字节哈希 + content_sha256 双校验）

#陷阱后果现状
